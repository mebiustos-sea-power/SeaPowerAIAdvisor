# AI Advisorのプロンプト見直しとチューニング

2026年10月25日 JST。AI Advisor全体のプロンプトを、プレイヤーの判断とゲームプレイへの有用性を起点に見直す。主力の評価・調整モデルは通常版の`deepseek/deepseek-v4.1-flash-1017`とし、`z-ai/glm-5.3`を比較対象として残す。

**指示を追加することと同じくらい、重複・曖昧さ・不要な制約を取り除くことを重視する。** 最近の個別不具合だけを起点にせず、通常相談・クイック相談・操作依頼を含む全体の振る舞いを評価する。

初期棚卸し後、第1回66相談と第2回50相談で比較・改訂を行った。第2回の候補s3_groupedを戦闘の根拠説明1項目へ正式反映し、ゲーム環境へ配置した。保存済みAPI接続・製品の既定モデルは変更していない。

## 評価する四つの製品価値

| 優先順位 | 製品価値 | 評価する内容 |
| --- | --- | --- |
| 1 | 相談意図に合う支援 | 質問、指定対象・地点、求められた範囲を守る。助言・事実確認・操作依頼を適切に扱う。 |
| 2 | プレイヤーの判断に役立つ内容 | 任務と戦況に照らした優先順位、理由、利害、不確実性を示す。判断を変える重要な不足を見落とさない。 |
| 3 | 理解しやすく行動につながる具体性 | 対象・行動・場所を特定できる。根拠のない細部や不要な作業を増やさない。必要な操作提案を提出する。 |
| 4 | プレイ中の使いやすさ | 質問に適した分量と自然な表現、会話の継続性、応答速度、API要求数とトークン負担を評価する。 |

プレイヤー既知情報の境界、事実と推測の区別、操作の承認と結果の正確な説明は、全体を支える品質条件とする。短さやツールの成功率だけで良否を決めない。

## 対象と責務

同梱JSONだけでなく、コードが組み立てる指示・ツール定義・取得結果の説明まで、AIへ実際に渡る経路を確認する。

| 対象 | 所有する内容 | 棚卸しの観点 |
| --- | --- | --- |
| `package/Prompts/common.json` | 共通の役割、助言方針、根拠、取得方針、ユーザー希望の扱い | 全相談に必要なルールか。回答を一律に狭めていないか。 |
| `package/Prompts/battle.json` | 戦闘の情報解釈、取得案内、リンクと操作に関する説明 | 共通ルール・データ説明・操作説明の重複と境界を確認する。 |
| `package/Prompts/campaign.json` | キャンペーンの情報解釈と取得案内 | 戦闘と共有すべき原則、キャンペーン固有の意味を分ける。 |
| `package/Prompts/requests.json` | クイック相談などの依頼文 | 相談名・ユーザーが期待する用途と依頼内容が合うか。 |
| 相談入力の構成 | 指示の追加・除外、情報取得方式、バッジ、会話履歴 | ファイルの文字列だけで判断せず、実際の入力を確認する。 |
| ツールと取得結果 | 名前、引数、説明、状態、エラー、データ項目の意味 | 実装上の契約と説明が一致し、迷わず呼び出せるか。 |
| コマンド定義 | 操作固有の条件・計画・提案ポリシー | 共通側に操作固有のルールを持ち込んでいないか。 |
| アドバイザーと共通希望 | 既定の性格・口調、ユーザーの追加希望 | 製品の基本動作と表示上の希望が適切に分かれているか。 |

コードが強制する権限・情報境界・承認・検証を、プロンプトによる指示だけへ移さない。データ取得や公開SDKの責務分離を維持し、文案の都合だけで構造を複雑化させない。

## 作業手順

1. **棚卸し**: 指示の配置と送信条件を確認し、維持・削除・統合・言い換え・配置変更の候補を根拠とともに整理する。
2. **試験設計**: 四つの製品価値を広く確認できるケースと、既知の失敗を確認するケースを選ぶ。変更する文言と狙いを明示する。
3. **一時プロンプトで反復**: 現行と候補を比較し、結果を受けて文案を修正する。単に一つの文案を繰り返すだけで終了しない。独立した変更を一度に混ぜすぎない。
4. **比較と回帰確認**: 有望な候補はGLMでも確認し、通常相談・クイック相談・操作依頼への副作用を確認する。目立つ一例だけで採用しない。
5. **正式反映**: 採用する文案と根拠を提示し、反映の依頼後に同梱プロンプトを更新する。関連するオフライン確認とゲーム環境への配置を行う。

1〜4を66相談の許可内で実施した。追加試験や正式反映は別途依頼に従う。過去の別試験で残った許可回数は流用せず、コミットとプッシュも別の許可として扱う。

## 削減と整理の判断基準

- 同じ意味の指示が複数箇所にあれば、適用範囲と送信タイミングを確認し、適切な所有者へ寄せる。別の経路でしか送られない説明は、見かけの重複だけで削除しない。
- 固定の返答量・構成・確認手順は、製品価値や実際の制約に必要な範囲へ絞る。通常助言のための制約が、比較説明や操作計画を妨げていないか確認する。
- データの意味は、そのデータを読む場面で分かる配置を検討する。ただし、移動後も各送信方式と既存の取得経路で必要な説明が届くことを確認する。
- ツール引数の仕様と同じ説明を重ねる場合は、モデルが間違えやすい意味や手順の補助になっているかを判断する。
- 誤りの原因をプロンプトだけに決めつけない。取得値・形式・データ不足・モデルの解釈を区別する。
- 削除・統合による効果も試験する。文字数・通信バイト数と、実際の入力トークン数・往復数・待ち時間は分けて記録する。

## 試験条件と記録

同じ質問の現行・候補比較、およびモデル間比較では、同じセーブ状態、質問、バッジ、戦況データの渡し方、操作許可、会話履歴、人物設定、通信・出力上限を使う。送信方式を変える試験は、文案やモデルの比較と分ける。フォールバックで別接続へ移った結果を同じモデルの成功として数えない。

2026年10月25日の19相談によるモデル比較は出発点の資料とする。当時、護衛セーブでは候補取得の例外により操作ツールを両モデルでOFFにした。その例外は`e2ce618`で修正済みであるため、今後の護衛セーブでの操作試験は新しい条件として記録する。

試験には、広い戦況相談、現在値だけの質問、利害の比較、会話の続き、座標・相対位置、操作の依頼を含める。既知の誤りに合わせた確認と、その他の相談の有用性を評価する確認を両方残す。採点をソノブイ操作だけに限定しない。

| 記録項目 | 内容 |
| --- | --- |
| 目的 | 何を改善・確認するか。対応する製品価値。 |
| プロンプト | 現行・候補の原文と日本語訳、変更箇所、削除した指示。 |
| 質問と条件 | 質問全文、バッジ、セーブ、モデル、送信方式、操作許可、履歴、その他の変更条件。 |
| 結果 | AIの回答全文、取得・提出の要約、成功・未完了・エラー、受理された実際の提案。 |
| 性能 | 相談全体の時間、実際のAPI要求数、報告された入力・出力トークン数。欠測は欠測として残す。 |
| 評価 | 正確性、意図遵守、有用性、説明と提案の一致、速度と負担、採用・継続・見送りの根拠。 |

操作の提出成功、ユーザーの採用、ゲームへの予約登録、実際の投下完了は別の到達点として記録する。主に提案までを試験し、実操作が必要な検証は対象と範囲を明示する。未完了を短時間での成功として扱わない。

## 現行の構成と送信経路

基準は`main`の`e2ce618`。4つのJSONには計133個の文字列項目がある。これにはクイック相談、取得カタログ、エラー、接続試験、互換経路の説明も含まれ、133項目すべてを各API要求へ送る構成ではない。

| ファイル | 文字列項目数 | 現在の主な適用範囲 |
| --- | --- | --- |
| `common.json` | 17 | 共通指示、希望の優先順位、送信方式・読み取りツールの説明 |
| `battle.json` | 57 | 戦闘の共通指示、取得説明・エラー、リンク、操作の説明 |
| `campaign.json` | 49 | キャンペーンの共通指示、航空情報の意味、取得説明・エラー |
| `requests.json` | 10 | クイック相談、接触評価・再評価、接続試験 |

`AdvisorPrompts.Instructions()`が共通指示にモード別の根拠・取得指示を加える。戦闘ではリンク指示も加わる。`AdvisorContext.Create()`はこれをsystem側へ移し、userデータから`instructions`と`query_tool`を取り除く。`common_prompt`、人物の希望、会話履歴、質問は別のuserデータとして渡る。基本指示をsystemとuserへ同時に複製する構成ではない。

| 戦況データの渡し方 | 指示とツールの構成 |
| --- | --- |
| 必要に応じて取得 | 共通の取得方針とモード別の取得案内、取得カタログ、`query_situation`を渡す。 |
| 最初にまとめて送信 | `retrieval_policy`を一括送信用へ差し替え、モード別`retrieval`を外す。`situation_data`を渡し、個別の戦況取得ツールとカタログを外す。 |
| 要求時にまとめて送信 | `retrieval_policy`を要求時の一括取得用へ差し替え、モード別`retrieval`を外す。初期戦況を外し、`get_situation`で一度だけまとめて返す。 |

操作が許可される場合は、上記に`list_operations`、`describe_operation`、`get_operation_candidates`、`propose_operation_plans`が加わる。候補取得は定義・提案ポリシーも返すため、候補取得と定義取得を必ず別々に行う必要はない。戦況は相談開始時の固定情報で、操作候補は照会時の状態を扱う。

標準ソノブイ操作の実装が、引数の意味・実行条件・投下順・追記と置換を所有する。目標2案、受理1～2案、単数選択は実際の操作定義から渡る。汎用の提出ツールが案数の解釈と完全な計画の一括提出を説明する。この責務分担を維持する。

標準プロバイダーは分割されたツールを使い、公開アダプターも`ToolsJson`へ統一した。旧共通バッチ専用の説明は互換経路とともに削除した。`battle.operation_tool_description`は独立型の操作ゲートウェイでも使うため維持する。NanoGPTの各API要求で文脈を再送する通信仕様は、同じ要求内の指示の重複とは分けて扱う。

以上の構成はコードに加え、以前のモデル比較で記録した初回リクエストを、3方式・操作許可ON/OFFについて照合した。人物の新規既定値は`Calm, professional and courteous.`で、基本プロンプトとは別の希望として渡る。

## 維持する境界と後で判断する課題

- 根拠、観測時刻、未取得値、設定で無効にした情報、既知の敵味方と種類の識別は維持する。ルールの配置や表現を整理しても意味を弱めない。
- 単なる挨拶、事実確認、助言、比較、操作依頼を、同じ回答形式や同じ取得量へ固定しない。
- 「未承認の提案」と「実行済み」を区別し、実際の提出結果と回答の内容を一致させる。置換が既存予約を消すことも曖昧にしない。
- 複数ユニット、外部コマンド、戦闘以外のモードに適用できる構造を維持する。共通指示へ特定コマンドの引数や数値を埋め込まない。
- コマンド定義・候補の構造、引数の検証、承認・二重実行防止は、プロンプト改善のために緩めない。
- `requests.json`の接続試験、互換経路の説明、UI向けのコマンド翻訳は用途が異なる。通常相談へ送られない文を削っても通常相談の負担削減にはならない。
- 既定の性格・口調とユーザー設定の優先順位は現在の分離を維持する。基本動作の評価後に、通常のMichael Reed設定でも確認する。

`AdvisorPrompts.WithText()`は一時編集の空文字を許容するため、単独の指示を外す試験ができる。一方、正式JSONは必須項目・非空文字列を検証する。文案の統合とJSONキーの廃止は別の変更であり、正式反映時に空文字やキー削除だけを行わない。

操作のエラーがコードだけで返る部分や、ソノブイのカタログ・定義・候補で同じ説明を返す部分もある。回復手順や通信量に問題が残る場合は、情報の返し方の改善として扱う。棚卸しを理由に公開契約や内部構造を先に作り替えない。

## 次の一時試験で確認する内容

最初は共通taskと助言方針の削減・置換を中心にする。新しいルールを多数追加する前に、既存の制約を外したときの有用性と副作用を確認する。その後、取得手順の整理、根拠とデータ解釈の説明へ進む。

| 確認する相談 | 主な観察点 |
| --- | --- |
| 現在値だけを求める質問 | 正しい値と必要な範囲だけを答え、不要な操作照会や提案をしない。 |
| 主なリスクと次の行動 | 優先順位と理由が分かり、二つの用途が保たれる。 |
| 運用の利点・不利益の比較 | 説明制限を外すことで、必要な比較と推奨理由が得られるか。 |
| 挨拶と会話の続き | 無用な戦況取得をせず、前の発言を根拠のない現在値として扱わない。 |

### 採用判断

**共通・戦闘プロンプトを広く置き換える候補を、そのまま正式採用することは勧めない。** 説明制限の削減、意図中心の置換、データ意味の統合、ID/取得説明の整理などを順に試したが、四つの製品価値を総合した安定改善は確認できなかった。これは一律の説明制限が最適と証明されたという意味ではなく、今回の候補を採用する根拠が不足しているという判断である。

### 残った問題と次の検討

優先順位は、まず依頼の達成、次に判断を変える誤り、そのうえで説明量と待ち時間とする。今回の結果だけを理由に、特定の一件に合わせたルールを共通プロンプトへ積み重ねない。

- 座標を正しく引用しながら相対方位を誤る例、現在針路と予約経路を混同する例、作動センサーの見落としが残る。解釈の説明と計算支援の要否を別途検討する。今回は計算用機能やデータ形式を変更しない。
- 敵味方と艦級の区別は一覧試験でも維持できた。自軍一覧は8ユニットを列挙したが、航空機見出しの機数や高度の混同があった。製品全体の評価を操作の提出率だけに絞らない。
- 次に試すなら、共通指示は一度現行を基準とし、操作側の「全案が条件に適合する」「提出後にMODが承認を受け付ける」「移動も含む予約」のうち一つずつを切り出す。今回の最終候補も複数の変更を含むため、どの一文が有効かまでは分離できていない。
