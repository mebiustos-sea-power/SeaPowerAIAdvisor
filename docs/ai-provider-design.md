# AIプロバイダー対応と相談実行方式の設計メモ

2026年10月19日時点の要件と設計案。Gemini以外の接続先、特にWindows上のOllamaとQwen3 8Bへの対応、および第三者MODによる拡張を扱う。要件と段階ごとの実装を以下に分ける。現行の期限・初期値・標準回答形式は第4段階、公開APIと外部登録は第5段階を参照し、それ以前の段階記述は各実装時点のものとして読む。公開契約版1を実装済みで、互換性の扱いと利用手順は[公開APIガイド](public-api.md)にまとめる。

基本方針は、ゲーム情報の意味と取得境界を共通化し、AIへの情報表現・通信形式・相談の進め方には拡張の余地を残すこと。共通相談エンジンは標準実装として提供し、すべての拡張に使用を強制しない。

地形情報の取得経路、地域単位の提供方法と送信量の比較は、[地形情報の取得とAIへの提供に関する調査](terrain-data-research.md)を参照する。

## 目的とユーザーの要求

ユーザーは利用コストの選択肢として、WindowsにOllamaを導入し、Qwen3 8BをローカルHTTPで利用する案を評価している。同時に、ローカルか外部サービスかにかかわらず、複数のAPI提供元へ対応できる構成を求めている。

要求は次のとおり。

- Interactions APIなどの固有処理を、各接続先の実装へ閉じ込める。
- API接続の登録時に提供元を選択でき、必要な設定項目を自然に表示できるようにする。
- 他の開発者がAnchorChain経由の追加MODとして接続先を追加しやすくする。
- 独自実装者が、既存方式よりよい情報表現や通信方法を採用できる自由度を残す。
- プレイヤーが知り得る情報だけを提供する方針を維持する。

本メモではAPI接続の提供元を「プロバイダー」と呼ぶ。Gemini APIやOllamaがプロバイダーであり、Qwen3 8BはOllamaなどで実行するモデルに当たる。Ollama対応をQwen3専用実装にはしない。

## 分離前の実装

設計検討開始時の製品はGemini専用。分離前の主な責務は次のとおり。

| 実装 | 現在の責務 | 共通化時の扱い |
| --- | --- | --- |
| `IAdvisorQuerySession` | ゲームモードから切り離した初期情報と問い合わせ結果の提供 | 許可された情報の取得窓口として活用する |
| `GeminiAdvisor` | 初期入力の構成、取得の往復、上限、進捗、Geminiの継続ID、サブ移行時の文脈構成 | 共通の相談制御とGemini固有処理を分ける |
| `GeminiInteraction` | Interactionsリクエストの構成と応答の解釈 | Gemini実装が所有する |
| `GeminiTransport` | 固定Google URLへのHTTP送受信、認証、通信エラーの分類、送受信ログ | Gemini実装が所有し、共通の診断・中止の契約と接続する |
| `GeminiFallback` | メインからサブへの移行と実送信回数 | プロバイダーをまたぐ接続選択の方針を共通化する |
| `AdvisorApiLibrary`とAPI設定画面 | 名前、キー、モデルの登録とメイン／サブ割り当て | 提供元の識別と固有設定を扱える形へ拡張する |

分離前の初期入力には戦況データ・指示・ツール定義がまとまっていた。これをそのまま公開された共通リクエスト型として固定せず、意味の異なる要素を分けて受け渡す方針とした。

既存の実装型は多くが`internal`であり、第三者向けのプロバイダー登録口はまだない。

参照するソースは[情報取得の契約](../src/Advisor/Consultation/IAdvisorQuerySession.cs)、[Geminiの接続構成](../src/Advisor/Providers/Gemini/GeminiService.cs)、[Interactions形式](../src/Shared/AI/Gemini/GeminiInteraction.cs)、[接続設定](../src/Advisor/Configuration/AdvisorApiLibrary.cs)、[MODの入口](../src/Plugin.cs)。

## 第1段階の実装

`feature/multi-provider-support`で、既存Gemini接続の動作を維持するための内部境界を実装した。公開SDK、外部登録、Ollama接続、提供元別の設定画面は後続作業とする。現在のインターフェースはすべて内部用であり、第三者向けの互換性契約としてはまだ固定しない。

| 実装 | 責務 |
| --- | --- |
| `AdvisorContext` | 質問、人物設定、共通希望、履歴、システム指示、ツール定義を準備し、情報取得窓口と相談期限を保持する |
| `IAdvisorBackend` | 標準エンジンの使用を必須にしない、相談実行部の内部契約 |
| `AdvisorEngine` | 標準の取得往復、結果の対応付け、進捗、中止、期限、取得・送信量制限、利用量の集計 |
| `IAiProvider`と`IAiProviderSession` | 分離された入力から接続セッションを作り、回答・ツール要求・結果を受け渡す内部契約 |
| `AiProviderRequest` | APIのJSONを共通側へ公開せず、送信前にバイト数を検査してから実送信するための境界 |
| `AiConnection` | メイン／サブの移行と実送信回数、接続セッションの破棄、共通の接続エラー |
| `AdvisorConsultation` | プロバイダーや相談方式に依存しない、完了・中止・失敗のログ記録 |
| `GeminiProvider` | Interactionsの継続ID、初期入力・取得結果のAPI表現、サブ移行時のGemini向け文脈構成 |
| `GeminiAdvisor` | 既存Gemini設定からプロバイダー、共通エンジン、HTTPとログの所有関係を組み立てる入口 |

`GeminiFallback`は`AiConnection`へ置き換えた。初期情報・指示・ツール定義は別々に渡し、共通エンジンと接続切り替えはInteractionsのリクエスト形式・継続ID・APIキーを扱わない。サブへ渡すのは本体が実行した取得要求と結果、および使用済みの取得回数であり、元プロバイダーの会話状態ではない。

既存のGemini形式とHTTP境界のテストを維持し、Gemini形式を使わない模擬プロバイダーで、並列結果の対応、別プロバイダーへの引き継ぎ、取得回数・送信量の制限を追加検証した。実API接続とゲーム内での動作は、ゲームへ配置した段階で確認する。

2026-10-31更新：標準相談エンジンの累積送信量1,000,000バイト制限は廃止した。履歴の再送やサブ接続への切替で累積量を超えても、それだけを理由に相談を停止しない。設定されたAPI通信回数、情報取得量、応答サイズ、タイムアウトなどの制限は維持する。`AiProviderRequest.Bytes` は画面翻訳・Reportsの個別要求サイズの検証でも使用するため残す。上記の送信量検査に関する説明は第1段階の実装当時の記録。

## 第2段階の実装：相談実行部の登録・選択

本体内部の`AdvisorBackendRegistry`へ相談実行部の設定準備処理を登録し、IDで選択できるようにした。MOD入口でGeminiを既定として登録し、戦闘・キャンペーンの会話画面に同じレジストリを渡す。会話画面は選択した実装を準備して共通ホストを呼び、Geminiの相談処理や標準エンジンを直接生成しない。

現在の登録・選択は本体内部用であり、第三者MOD向けの公開SDKや設定画面の選択肢ではない。別MODからの登録、提供元別の設定保存とUI、Ollama接続は後続作業とする。現在の設定画面は引き続き既存Gemini設定を編集する。

| 実装 | 責務 |
| --- | --- |
| `AdvisorBackendRegistry` | 実装の登録・選択と、選択した実装だけの設定準備。未登録IDや重複登録は明示的なエラー |
| `AdvisorBackendSetup` | 1回の相談へ固定する設定、モデル情報、期限、診断情報と実行スコープの生成処理 |
| `AdvisorBackendHandle` | 相談実行部と、その通信・独自リソースの破棄 |
| `AdvisorConsultation` | 共通の期限・中止の確認、実際の情報取得回数の採用、結果・中止・失敗の記録と実行スコープの破棄 |
| `IAdvisorBackend` | 任意の通信回数・情報表現・ツール構成・取得手順で相談を実行する契約 |
| `AdvisorEngine` | 段階取得を使う実装が任意で再利用する標準の往復処理 |
| `GeminiBackend` | 既存Gemini設定の読込、標準エンジンとGeminiアダプター・通信処理の構成 |
| `AdvisorTraceOptions` | 提供元に依存しない診断の有効化、API識別・モデル情報・秘密値の除去設定 |

登録は設定準備の関数を保持し、準備時は接続やログ書込みを開始しない。相談を開始した時点の準備結果を保持するため、選択や設定の変更は次の相談から反映する。選択されていない実装の設定は読み込まず、選択した実装の設定不備や例外を別の実装で隠さない。実行スコープの生成は同期のリソース準備に留め、実際の通信はキャンセル可能な`ConsultAsync`内で行う。

独自実装は`IAdvisorBackend`を実装すればよく、`AdvisorEngine`や`IAiProvider`を使う必要はない。本体内部では次の形で登録・選択する（公開APIの利用例ではない）。

```csharp
Plugin.Backends.Register("custom", PrepareCustomBackend); // Func<AdvisorBackendSetup>
Plugin.Backends.Select("custom");
```

独自実装も`AdvisorContext.Knowledge`を通して情報を取得する。ユーザーの情報選択、取得対象・引数・回数・返却量の検証は従来の情報取得窓口に残る。共通ホストは返答の取得回数を窓口の実績から作る。標準エンジンの「取得上限+最終回答1回」というAPI要求回数制限は独自実装に強制せず、通信回数と情報取得回数を区別する。独自実装も渡された中止トークンに応答することを契約とし、任意の実装を強制終了できるとは扱わない。

全送受信ログには、各実装が実際の送受信を渡す共通の診断窓口を使う。Geminiのログ形式・秘密値除去・既存の接続テストは維持し、独自実装の成功・中止・例外は共通ホストが記録する。メイン／サブ移行は標準エンジンが従来どおり共通接続部を利用する。独自の相談実装による接続移行の組立ては標準の往復処理に固定しない。

Geminiの全既存テストに加え、標準エンジンを使わない模擬実装で、独自の通信手順と情報取得制約、実行中の設定保持、失敗の可視化、期限とユーザー中止の区別、リソースの破棄、独自ログの秘密値除去を検証した。登録したGeminiも模擬HTTPで既存のInteractions形式と相談ごとの設定読込を確認した。全224チェック、DCMを読み込まない別プロセスで66チェックが成功。この版をゲーム環境へ配置した後、ユーザーが既存Gemini接続を確認し、問題なさそうだと報告した。エージェント自身による実API接続や、全条件を網羅した実ゲーム検証を意味するものではない。

## 共通化する情報と自由に変更できる表現

構造化されたゲーム情報は共通の資産とする。JSONは現在の表現形式であり、Gemini固有の仕様ではない。一方、共通JSONをそのままAIへ送る義務は設けない。

| 内容 | 所有する側 |
| --- | --- |
| 勝利条件、位置、弾薬、損傷、観測済み接触、公開性能などの意味 | 本体の情報取得層 |
| 安定した識別子、英語の項目名・状態コード、ゲーム画面と同じ名称、未知と正常の区別 | 本体の共通情報表現 |
| 取得可能な情報、問い合わせの意味と引数・結果のスキーマ | 本体の情報取得層 |
| 質問、回答言語、人物設定、共通プロンプト、提供する会話履歴 | 本体が提供する相談の共通要素 |
| AIへ公開するツール名・ツール登録形式、情報の符号化、メッセージへの配置 | プロバイダーまたは独自の相談実装 |
| 継続ID、署名、認証、API固有の履歴、応答形式 | 各プロバイダー |

例えば同じ弾薬情報を、Geminiでは`function_result`へ、Ollamaではツール結果メッセージへ格納できる。独自実装では別の表現へ変換したり、最初にまとめて送ったりしてよい。AIに見せるツール構成も、内部の問い合わせ名をそのまま公開する方式に限定しない。

変換後も、既知と推定、正常と未取得、標準搭載候補と実搭載、在庫と発射準備済み数などの区別を維持する。AIへの送り方の工夫によって、情報の取得範囲が広がるわけではない。

## 相談実行方式の拡張

最初に検討した「共通相談エンジンとAPIアダプター」は、既存の相談方式を使って接続先を追加する用途に適している。その後、ユーザーから独自実装者による新しい通信アイデアを受け入れる必要が提示された。この要件では、相談の往復方式まで標準エンジンに固定する境界は狭い。

拡張口を次の二段階に分ける案を推す。

| 拡張口 | 想定する実装者 | 自由に変更する範囲 |
| --- | --- | --- |
| 標準相談エンジン用のプロバイダーアダプター | 既存の段階取得を使って接続先を追加したい開発者 | API変換、通信、プロバイダー固有の状態と設定 |
| 相談実行部の差し替え | 情報の渡し方そのものを工夫したい開発者 | 情報の選別・表現、ツール構成、API往復、履歴・キャッシュの利用方法 |

標準経路は、共通エンジンが質問と指示を渡し、回答本文または追加情報の要求を受け取る構成とする。Geminiの継続IDやOllama向けの履歴構成は各アダプターが所有する。

独自経路には、相談開始時の共通要素と、許可された情報を取得する窓口を渡す。独自実装が取得の進め方と送信方法を組み立て、本体の会話画面へ最終回答や進捗を返す。標準相談エンジンの利用を必須にしない。

第5段階では、標準アダプターと独自相談を別インターフェースとして公開した。共通の設定・情報取得・診断・中止を利用しつつ、標準の往復制御の利用は任意とする。

## 本体が維持する境界

どちらの拡張方式でも、本体が提供する情報取得窓口は同じ制約を適用する。

- プレイヤーが知り得る情報だけを返し、敵の実オブジェクトや非公開の状態を渡さない。
- ユーザーの情報選択、問い合わせの検証、取得上限を適用する。
- 相談の識別と対象のスナップショットを本体が管理し、AIや接続実装に任意の内部ゲーム状態を指定させない。
- 中止、接続別の通信期限、進捗、診断ログ、失敗の報告について共通の契約を設ける。

独自実装が情報を取得する際も、この窓口を使う。公開契約へUnityのゲームオブジェクトを渡さない。通信や相談の内部状態を自由に実装できることと、提供情報の制限を外せることを分ける。

設定の不整合、必要機能の欠落、予期しない例外は、別プロバイダーへの正常な切り替えで隠さず、原因を確認できるエラーとして扱う。

## 第3段階の実装：提供元別の接続設定とOllama

`AdvisorServices`が標準バックエンドを構成し、保存済みのメイン／サブからそれぞれの提供元を解決する。`AdvisorBackendRegistry`の独自実装への切り替え機能は維持し、標準エンジンの利用を強制しない。第1・第2段階の「Ollama／設定UIは後続」という記述は、その段階での状態を表す。

| 実装 | 責務 |
| --- | --- |
| `AdvisorService`／`AdvisorServiceCatalog` | 提供元の識別、入力項目・初期値・秘密値指定、検証、標準経路の接続生成と接続テスト |
| `AdvisorApiLibrary` | 登録ID・名前・提供元ID・固有設定とメイン／サブ割り当ての保存 |
| `AdvisorApiSettingsView` | 提供元が宣言した入力欄の生成、伏せ字入力、編集中の提供元切り替えと破棄 |
| `AdvisorServices` | 相談開始時の設定固定、標準エンジンと提供元の組み立て、接続テストの共通操作 |
| `AiHttpTransport` | 中止・要求期限・受信量制限・JSON読込・HTTPエラー・通信ログ。URLと認証ヘッダーは呼出元が指定 |
| `GeminiService`／`GeminiProvider`／`GeminiTransport` | Geminiの設定検証、公式URLと認証、Interactionsの継続・ツール形式 |
| `OllamaService`／`OllamaProvider` | OllamaのURL／モデル／文脈長の検証、ネイティブChat API、メッセージ履歴・ツール要求・結果・利用量 |

現在の入力部品は通常テキストと伏せ字。数値の文脈長も文字入力として保持し、Ollama側で数値範囲を検証してAPIでは整数へ変換する。提供元固有のURLやモデルの規則を画面コードの分岐にしない。APIキーはPasswordBoxを使い、入力直後の文字の一時表示も無効にする。

### 既存設定の引き継ぎ

接続設定ファイルは`api-settings.json`とする。起動時にこのファイルがあれば使用し、旧`gemini.json`もある場合は旧ファイルへ触れない。新ファイルがなく旧ファイルがある場合だけ、内容を変えずに名前を変更する。両方なければ初期状態で開始し、次の保存から新ファイルを使う。移行に失敗した場合は`settings_migration_failed`を起動時の障害としてログへ記録し、初期化や別ファイルへの切り替えで隠さない。新ファイルが不正でも旧ファイルへ戻さず、通常の設定読込エラーとする。

このファイル名の移行と、JSONの保存形式の移行は分ける。旧キー／モデル形式とschema 2の登録形式は読み込み時にGeminiとして解決する。JSONは読むだけでは書き換えず、登録・割り当て・ログ設定などの保存時にschema 3で記録する。登録ID、名前、キー、モデル、メイン／サブの割り当て、既存の期限／出力上限／ログ設定を保持する。

schema 3の登録項目は`id`、`name`、`provider`、`settings`。`settings`を提供元が所有する。未導入の提供元の設定は、他の設定を保存しても消さない。選択した接続の提供元が不明な場合は`provider_unavailable`を表示し、別提供元へ自動的に読み替えない。既知の提供元の設定不備も検証エラーとして表示する。

schema 3を保存すると、以前のリリースはその形式を読めない。実ゲームでの比較試験に配置する際には、旧版へ戻せるよう設定の退避を別途検討する。この実装作業では実際のユーザー設定を読み書きしていない。

### Ollamaの設定と通信

- 提供元：Ollama。
- サーバーURL：初期値`http://localhost:11434`。HTTP／HTTPSとリバースプロキシのパス接頭辞を許可し、末尾へ`/api/chat`を追加する。URL内の認証情報、クエリ、フラグメントは受け付けない。
- モデル：初期値`qwen3:8b`。導入済みのツール呼び出し対応モデルを指定する。Qwen3専用のモデル名照合は行わない。
- コンテキスト長：初期値32768トークン、指定範囲4096～262144。APIの`options.num_ctx`へ渡す。長い文脈のメモリ使用量と実際の回答能力はモデル・実行環境によって異なる。

`stream:false`でChat APIを呼び、初期指示とプレイヤー既知の入力をsystem／userメッセージへ設定する。複数のツール呼び出しを既存の情報取得窓口でまとめて実行し、assistantメッセージと各tool結果を次の要求へ渡す。思考対応モデルの`thinking`は後続要求の会話状態として保持するが、回答本文には混ぜない。思考モード自体はモデルの既定値に従い、全モデルへQwen固有の設定を強制しない。

最大取得回数後はツール定義を外して最終回答を求める。除外した情報、ID、取得回数・送信量の制限は従来の共通境界で検証する。利用量は`prompt_eval_count`と`eval_count`の両方が有効な場合に加算し、欠落をゼロへ置換しない。この数値からGeminiと共通の請求額は作らない。

APIキーは不要。Ollamaのインストール、モデルのダウンロード、サーバーの起動・終了は本MODから行わない。接続テストは短いテスト文だけを送り、戦況・プロフィール・会話履歴・ツール定義は送らず、設定の登録や選択も確定しない。

既存の共通期限は維持し、未指定時は1要求60秒・相談全体180秒。低速なローカル実行では到達し得る。現状の手動設定範囲は`request_timeout_seconds`が5～120、`consultation_timeout_seconds`が10～600で、全体期限を要求期限以上とする。Ollama専用の長時間無制限実行は導入しない。

### 提供元をまたぐサブ接続

## 第4段階の実装：通信期限と標準回答形式

## OpenRouterへの対応

提供元ID `openrouter` を既存の標準エンジンへ追加。接続設定は伏せ字のAPIキーと自由入力のモデルIDを持ち、既定モデルは `google/gemini-3.5-flash-lite`。APIのURLは `https://openrouter.ai/api/v1/chat/completions` に固定する。説明文は既存の任意メタデータを使い、ツール対応条件とモデル名の例を英日で表示する。

## NanoGPT定額接続

提供元IDは`nanogpt`、通信識別子は`nanogpt_subscription_chat`。APIキー・モデル名・接続ごとの出力トークン上限を登録し、例示初期モデルは`deepseek/deepseek-v4.1-flash-1017`とする。モデル一覧を固定せず、定額対象／ツール対応の判定はサービスと既存の接続テストへ委ねる。

出力上限は提供元固有の`settings.max_output_tokens`へ整数の文字列で保存し、NanoGPT側が正の整数として検証して送信時の`max_tokens`へ変換する。新規接続の初期値は4096。推論もこの出力枠を消費する。モデルごとの実上限はサービス側で検証され、MODは旧共通設定の8192上限をこの接続項目には適用しない。既存接続で未指定の場合は従来の共通上限を使い、編集フォームを開いた際も提供元の`EditSettings`がその値を補う。フォームを開いただけでは保存しない。保存・複製・接続テスト・メイン／サブ切り替えでも各接続の上限を維持し、相談中の値は開始時に固定する。他の提供元の出力上限や公開拡張契約は変えない。

OpenAI互換の履歴・ツール呼び出し／結果・不透明な応答メタデータの保持と、2段階接続テストを`Providers/ChatCompletions`へ共有する。各提供元はURL・要求固有項目・課金エラーの解釈を所有する。Gemini Interactions／Ollamaの処理や公開SDK契約は変えない。

## 接続別の戦況データ供給方式（2026-10-23 実装）

登録済み接続の共通項目 `situation_delivery` で `on_demand`（省略時の初期値）／`upfront`／`on_request` を選ぶ。プロバイダー固有の `settings` には入れない。編集・複製・保存は接続の属性として引き継ぐ。既存設定を読むだけでは保存しない。既存のプロバイダーメッセージ欄には、Geminiの前回Interaction IDによる継続、Ollama／OpenRouter／NanoGPTの各要求での履歴再送を短く記載する。

責務は次のとおり。

- `BattleSnapshotExport`／`CampaignSnapshotExport` は各情報取得セッションの一部として、既存の非公開 `Dispatch` と同じ許可・整形を用いて固定スナップショットを全件取得する。`AdvisorSnapshotExport` は内部のID分割・ページ送りと共通資料の重複排除だけを担当し、公開問い合わせの回数・返却予算を消費しない。生の診断JSONは送らない。
- `AdvisorSituationInput` が標準エンジンの一括入力を組み立てる。初期カタログと取得向け指示を置換し、許可済み全データを `situation_data` に載せる。戦況用スキーマを除き、WIP有効時の操作照会・実行提案は維持する。操作候補は必要時点のライブ照会のままで、戦況一括データに混ぜない。
- `AdvisorReadSession` が相談全体の情報量と読取の受付を所有する。一括送信中の戦況取得はデータなしの `situation_already_supplied` とし、操作照会は通常処理する。一括入力が既存160,000バイトの情報量上限を超える場合は送信前に明示エラーとし、部分送信や自動の方式変更はしない。
- `AdvisorEngine` は同じ相談ループを使用し、`AiConnection` の切替時入力ファクトリーを通じてメイン／サブそれぞれの方式を適用する。元のスナップショットと相談上限は維持する。各プロバイダーはJSON・会話ID・履歴などの通信形式だけを担当する。
- 独自相談処理には標準供給方式を強制せず、知識・操作の窓口を渡す。標準・独立型とも入力の定義一覧は`ToolsJson`を使い、ツールがない場合は空の一覧を渡す。

一括送信で消えるのは戦況の追加取得であり、操作照会・提案の往復や履歴再送は残る。入力トークン・応答品質の優劣は実測前に断定しない。接続テストは通信互換性の小さな試験のままとし、ゲームの全量データを送らない。

### 要求時の一括送信（on_request）

日本語UIは「要求時にまとめて送信」。初回は概要・目標・カタログ・バッジ参照の詳細・見解用の補足情報など、自動追加する戦況情報を外し、質問・ユーザー設定・指定範囲の会話履歴を維持する。戦況が必要な場合に引数なしのget_situationをAIが呼び、相談開始時に採取した許可済みスナップショットを全件返す。AIの要求時にゲームを再採取しない。操作一覧・定義・候補の照会はこの取得を発生させない。

AdvisorSituationInputが最小初期入力と既存一括生成処理を使う全量データの組立を所有し、AdvisorReadSessionが相談内の送信済み状態・予算を所有する。初回成功だけ全量を返し、以後はalready_suppliedとする。同一応答での複数要求にも全量を複製しない。全量の結果には既存160,000バイトの相談全体予算を使い、通常の応答は48,000バイト制限を維持する。取消・超過時は送信済みにしない。全量生成はupfrontと同じく個別取得回数query_roundsを消費しないが、API要求上限と同一応答8項目の制限は維持する。

成功した全量の取得記録を標準エンジンの継続履歴・独自相談への引き継ぎ・開発API診断へ残す。標準SDKにはget_situationとして全量取得を公開する。独自相談には新方式を強制しない。既存2方式・省略時の初期値・設定ファイル名は変更しない。初回の全量ツール結果の重複は防ぐが、各プロバイダーの履歴再送方式そのものは変わらない。

## 用途別Function Callingと内部構造の整理（2026-10-23）

標準エンジンのツールをquery_situation／list_operations／describe_operation／get_operation_candidates／propose_operation_plansに分割した。AdvisorToolBindingが定義と処理担当を組にし、AdvisorToolSessionが登録・呼び出しIDの対応・集約・順序を管理する。AdvisorReadSessionは正規化済み読み取りの実行と共通データ予算に限定し、操作スキーマと変換はAdvisorOperationToolsが所有する。AdvisorEngineは個別のツール名やsource／actionを判断しない。

AiProviderInputとGemini／Ollama／Chat Completionsの通信処理は任意長の定義一覧を扱う。公開契約2ではIStandardAdvisorExtensionがToolsJsonを受け取り、旧2ツール形式・移行用インターフェース・互換分岐を廃止した。標準・独立型とも同じ入力コンテナーを使い、独自相談の実行方式とKnowledge／Operationsサービスは維持する。接続切替でも実行済み情報と提案receipt、取得・送信予算を共有する。

操作ごとの登録・引数正規化・承認時検証・ゲームスレッド実行は既存担当へ残す。データ供給方式、情報選択、初回資料送信、上限時の未完了終了も維持する。目的は責務整理であり、実モデルでの精度向上や通信回数削減はこの構造変更だけでは断定しない。


## 相談ごとの操作利用許可（2026-10-23）

今回はOFF／許可の2段階。AdvisorShortcutがAllowOperationsを持ち、生成したAdvisorQuestionへ不変値として引き継ぐ。次の行動・主なリスク・攻撃提案・レーダー運用は許可し、説明用の詳しく、および見解／再評価はOFF。手入力とバッジ付き質問も許可し、コマンドごとの有効設定とゲーム側の可用性を上限とする。自軍／接触一覧のクイック相談は廃止し、情報取得ツール自体は維持する。IsShortcutという表示・下書き処理用フラグを操作可否の判定へ流用せず、文章からMODが操作の要否を分類しない。将来の独自クイック登録では同じ属性を初期OFFで選択可能にする想定だが、独自登録UI自体は今回追加しない。

AdvisorConsultationが許可を確認してから操作用セッションを作る。OFFではセッションを作らないため、一覧・定義・候補・提案の全操作ツールも、独自相談用の操作サービスも渡らない。各プロバイダーや個別コマンドへこの判定を分散しない。戦況データの供給方式と通常の助言は独立に維持する。許可ONは利用可能という意味で、実行を強制せず、承認や検証は従来担当のまま。

再試行は元のAdvisorQuestionを使い、接続切替は操作サービスがない同じ相談コンテキストを引き継ぐ。開発APIはallow_operationsの任意booleanと受理／結果の記録、CLIは--allow-operations／--no-operationsに対応する。省略時は相談の定義に従い、明示値はその相談のみ上書きする。会話履歴から許可を復元したり次の質問へ暗黙に引き継いだりしない。

強制（操作を要求）は、実運用で必要性が確認できてから再検討する。現時点では別のモード、成功判定、追加プロンプトを実装しない。


## クイック相談ごとの戦況データ供給方式（2026-10-23）

現在はユーザー向けの設定画面・保存項目を追加せず、AdvisorShortcutの不変な内部属性SituationDeliveryで指定する。既存6定義（現在の5ボタン＋開発API用の詳しく）はすべてupfrontを明示する。コンストラクターはnullableで、将来の独自クイックに接続継承／on_demand／upfront／on_requestを指定できる。独自クイック登録・編集機能を作る段階で選択UIを検討する。通常手入力は引き続き接続設定を使う。第4の送信enumやクイック別の設定ファイルは作らない。

AdvisorShortcut.Prepareが定義値をAdvisorQuestionへコピーし、受理済み指定は操作許可の変更と再試行でも保持する。開発APIの明示指定はこれを1相談だけ上書きできる。優先順位は開発API＞クイック内部定義＞接続設定。文章から操作や戦況取得の要否をMODが分類しない。

AdvisorBackendRegistryの共通準備窓口からAdvisorServicesへ指定を渡し、標準メイン／サブの不変な相談用設定を作る。明示指定は両接続へ適用、継承なら各保存値。開発APIは対象クイックを解決してから接続を準備し、APIキー・モデル・保存済み方式は変更しない。未対応の独自相談方式にupfront／on_requestを指定した場合は準備時に明示エラーとし、標準エンジンへ差し替えたり通常失敗として別接続へ隠したりしない。新しい指定を受け取れない旧内部バックエンドも黙って無視しない。公開SDK契約や個別プロバイダーの通信実装は変更しない。

開発APIの受理・保持結果はメインの有効situation_delivery、保持結果と開始ログはsituation_delivery_overrideを記録する。nullは接続継承で、実際の入力のinteraction_modeで接続切替後も追跡できる。既存の3供給方式・情報選択・一括データ予算・取得上限・操作許可・承認を再利用し、追加プロンプトは加えない。


## 接続別プロンプト（2026-10-26）

API接続の共通メタデータに任意の `prompt` を保存する。未設定・新規は空欄、上限2000文字。改行とタブを許可し、不正な型・制御文字・UTF-8へ変換できない文字列は `prompt_invalid` として表示する。登録・編集・未保存確認・複製は既存の接続フォーム/保存境界に従う。

相談開始時に取得した接続設定を使い、共通側が有効な接続の指示を `connection_prompt` としてAI入力へ追加する。空欄なら項目を送らない。共通/人物設定とは別項目で渡し、共通プロンプトとの競合時は接続別を優先する短い説明を `common.json` に置く。指示の内容解析・分類・競合判定は行わない。既存の人物表現ルールと基本ルールは維持する。

標準エンジンは戦況送信方式の準備後に追加し、サブ接続へ切り替わった際はサブの指示へ差し替える。独立実行方式の外部アダプターにも共通側で同じ項目を渡す。各アダプターの固有設定やSDK契約へ重複した項目は追加しない。接続テストは既存の専用指示を使い、接続別プロンプトを適用しない。AI入力診断と開発APIの入力記録にも反映する。
