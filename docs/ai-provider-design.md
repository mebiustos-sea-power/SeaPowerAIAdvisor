# AIプロバイダー対応と相談実行方式の設計メモ

2026年10月19日時点の要件と設計案。Gemini以外の接続先、特にWindows上のOllamaとQwen3 8Bへの対応、および第三者MODによる拡張を扱う。要件と現状を以下に分け、具体的な公開インターフェースや保存形式は未決定とする。

基本方針は、ゲーム情報の意味と取得境界を共通化し、AIへの情報表現・通信形式・相談の進め方には拡張の余地を残すこと。共通相談エンジンは標準実装として提供し、すべての拡張に使用を強制しない。

## 目的とユーザーの要求

ユーザーは利用コストの選択肢として、WindowsにOllamaを導入し、Qwen3 8BをローカルHTTPで利用する案を評価している。同時に、ローカルか外部サービスかにかかわらず、複数のAPI提供元へ対応できる構成を求めている。

要求は次のとおり。

- Interactions APIなどの固有処理を、各接続先の実装へ閉じ込める。
- API接続の登録時に提供元を選択でき、必要な設定項目を自然に表示できるようにする。
- 他の開発者がAnchorChain経由の追加MODとして接続先を追加しやすくする。
- 独自実装者が、既存方式よりよい情報表現や通信方法を採用できる自由度を残す。
- プレイヤーが知り得る情報だけを提供する方針を維持する。

本メモではAPI接続の提供元を「プロバイダー」と呼ぶ。Gemini APIやOllamaがプロバイダーであり、Qwen3 8BはOllamaなどで実行するモデルに当たる。Ollama対応をQwen3専用実装にはしない。

## 現在の実装

現在の製品はGemini専用。ローカルで確認した主な境界は次のとおり。

| 実装 | 現在の責務 | 共通化時の扱い |
| --- | --- | --- |
| `IAdvisorQuerySession` | ゲームモードから切り離した初期情報と問い合わせ結果の提供 | 許可された情報の取得窓口として活用する |
| `GeminiAdvisor` | 初期入力の構成、取得の往復、上限、進捗、Geminiの継続ID、サブ移行時の文脈構成 | 共通の相談制御とGemini固有処理を分ける |
| `GeminiInteraction` | Interactionsリクエストの構成と応答の解釈 | Gemini実装が所有する |
| `GeminiTransport` | 固定Google URLへのHTTP送受信、認証、通信エラーの分類、送受信ログ | Gemini実装が所有し、共通の診断・中止の契約と接続する |
| `GeminiFallback` | メインからサブへの移行と実送信回数 | プロバイダーをまたぐ接続選択の方針を共通化する |
| `AdvisorApiLibrary`とAPI設定画面 | 名前、キー、モデルの登録とメイン／サブ割り当て | 提供元の識別と固有設定を扱える形へ拡張する |

現在の初期入力には戦況データ・指示・ツール定義がまとまっている。これをそのまま公開された共通リクエスト型として固定せず、意味の異なる要素を分けて受け渡す。

既存の実装型は多くが`internal`であり、第三者向けのプロバイダー登録口はまだない。

参照するソースは[情報取得の契約](../src/IAdvisorQuerySession.cs)、[Geminiの相談処理](../src/GeminiAdvisor.cs)、[Interactions形式](../src/GeminiInteraction.cs)、[接続設定](../src/AdvisorApiLibrary.cs)、[MODの入口](../src/Plugin.cs)。

## 共通化する情報と自由に変更できる表現

構造化されたゲーム情報は共通の資産とする。JSONは現在の表現形式であり、Gemini固有の仕様ではない。一方、共通JSONをそのままAIへ送る義務は設けない。

| 内容 | 所有する側 |
| --- | --- |
| 勝利条件、位置、弾薬、損傷、観測済み接触、公開性能などの意味 | 本体の情報取得層 |
| 安定した識別子、英語の項目名・状態コード、ゲーム画面と同じ名称、未知と正常の区別 | 本体の共通情報表現 |
| 取得可能な情報、問い合わせの意味と引数・結果のスキーマ | 本体の情報取得層 |
| 質問、回答言語、人物設定、共通プロンプト、提供する会話履歴 | 本体が提供する相談の共通要素 |
| AIへ公開するツール名・ツール登録形式、情報の符号化、メッセージへの配置 | プロバイダーまたは独自の相談実装 |
| 継続ID、署名、認証、API固有の履歴、応答形式 | 各プロバイダー |

例えば同じ弾薬情報を、Geminiでは`function_result`へ、Ollamaではツール結果メッセージへ格納できる。独自実装では別の表現へ変換したり、最初にまとめて送ったりしてよい。AIに見せるツール構成も、内部の問い合わせ名をそのまま公開する方式に限定しない。

変換後も、既知と推定、正常と未取得、標準搭載候補と実搭載、在庫と発射準備済み数などの区別を維持する。AIへの送り方の工夫によって、情報の取得範囲が広がるわけではない。

## 相談実行方式の拡張

最初に検討した「共通相談エンジンとAPIアダプター」は、既存の相談方式を使って接続先を追加する用途に適している。その後、ユーザーから独自実装者による新しい通信アイデアを受け入れる必要が提示された。この要件では、相談の往復方式まで標準エンジンに固定する境界は狭い。

拡張口を次の二段階に分ける案を推す。

| 拡張口 | 想定する実装者 | 自由に変更する範囲 |
| --- | --- | --- |
| 標準相談エンジン用のプロバイダーアダプター | 既存の段階取得を使って接続先を追加したい開発者 | API変換、通信、プロバイダー固有の状態と設定 |
| 相談実行部の差し替え | 情報の渡し方そのものを工夫したい開発者 | 情報の選別・表現、ツール構成、API往復、履歴・キャッシュの利用方法 |

標準経路は、共通エンジンが質問と指示を渡し、回答本文または追加情報の要求を受け取る構成とする。Geminiの継続IDやOllama向けの履歴構成は各アダプターが所有する。

独自経路には、相談開始時の共通要素と、許可された情報を取得する窓口を渡す。独自実装が取得の進め方と送信方法を組み立て、本体の会話画面へ最終回答や進捗を返す。標準相談エンジンの利用を必須にしない。

これら二段階を、別インターフェースにするか、一つの相談実行契約と標準実装用ヘルパーで構成するかは未決定。外部実装の自由度を確保しつつ、同じ往復制御を毎回実装しなくて済む形を選ぶ。

## 本体が維持する境界

どちらの拡張方式でも、本体が提供する情報取得窓口は同じ制約を適用する。

- プレイヤーが知り得る情報だけを返し、敵の実オブジェクトや非公開の状態を渡さない。
- ユーザーの情報選択、問い合わせの検証、取得上限を適用する。
- 相談の識別と対象のスナップショットを本体が管理し、AIや接続実装に任意の内部ゲーム状態を指定させない。
- 中止、相談期限、進捗、診断ログ、失敗の報告について共通の契約を設ける。

独自実装が情報を取得する際も、この窓口を使う。公開契約へUnityのゲームオブジェクトを渡さない。通信や相談の内部状態を自由に実装できることと、提供情報の制限を外せることを分ける。

設定の不整合、必要機能の欠落、予期しない例外は、別プロバイダーへの正常な切り替えで隠さず、原因を確認できるエラーとして扱う。

## 接続設定とプロバイダーの登録

接続設定は共通の登録情報と、提供元が所有する固有設定に分ける。

| 共通の登録情報 | Geminiの例 | Ollamaの例 |
| --- | --- | --- |
| 登録ID、登録名、プロバイダーID | APIキー、モデル名 | サーバーURL、モデル名 |
| メイン／サブへの割り当て | Gemini固有の追加設定 | 文脈長、思考設定など |
| 接続テストの操作と結果表示 | Gemini用の検証と通信 | Ollama用の検証と通信 |

提供元を選ぶと、その実装が定義した設定項目を表示する。設定の意味・初期値・必須条件・検証はプロバイダー側が所有し、本体は文字入力、伏せ字、数値、選択肢などの共通部品を提供する案とする。新しいプロバイダーの追加ごとに本体へ個別の分岐を追加しない。

Ollamaの標準ローカルAPIは認証不要であり、APIキーを全接続共通の必須項目にはできない。モデルごとのツール呼び出し・思考設定などの対応状況も、プロバイダー名だけで一律に決めない。利用量を取得できない場合は不明とし、意味が異なる数値から共通の請求額を作らない。

第三者拡張の公開契約は、小さな契約用DLLへ分離する案とする。共通データ型と登録口を提供し、Unity、Noesis、Geminiの型への依存を持ち込まない。AnchorChainが追加MODをロードし、追加MODがAIAdvisorの公開APIへプロバイダーを登録する。AnchorChain自体へAI通信機能を追加する構成にはしない。

提供元が未導入でも、その接続の保存内容は保持する。「必要なプロバイダーが見つからない」と表示し、設定の削除や別提供元への読み替えをしない。登録のタイミング、依存関係、IDの重複、公開契約の互換性は実装時に定義する。

## メインとサブの接続切り替え

標準経路では、メイン／サブの選択と移行方針を共通エンジンが所有する。各プロバイダーは固有のエラーを共通の分類へ変換し、共通側が切り替え可否を判断する。

提供元を変更する際は、初期質問と取得済みの事実を引き継ぎ、元の提供元に属する継続IDや署名は渡さない。情報取得を最初からやり直さず、使用済みの取得枠も維持する。

ローカル接続から外部サービスへの移行も設定上で明確に分かるようにする。独自の相談実行部が共通の切り替え機構を利用する方法、独自の再試行と共通側の切り替えが重複しない契約は未決定。

## 実装範囲と検証の案

既存のGemini対応を維持しながら、共通の情報境界・相談契約・設定登録を整え、標準経路のGemini実装を移す。次にOllamaを同じ境界へ接続し、性質の異なる二つのAPIで構成が成立することを確認する。

さらに、相談の進め方を変更する小さな独自実装で、標準エンジンを使わず情報取得窓口と会話UIを利用できることを確認する。GeminiとOllamaだけで動いても、第三者向け拡張の自由度を検証したことにはならない。

OllamaにはローカルAPIとツール呼び出しの仕組みがあり、Qwen3もツール対応モデルとして提供されている。一方、このMODの長い入力と複数回の取得をQwen3 8Bがどの程度正しく処理できるかは、実ゲームで検証する。文脈長を増やすと必要メモリも増えるため、ゲームと同時実行した際の速度・メモリ使用量を確認する。

今後決める事項は次のとおり。

- 公開契約の粒度、データ型、ライフサイクル、互換性の扱い。
- 共通の往復・期限・進捗・ログ・切り替え機構を独自実装へ提供する方法。
- 固有設定の保存形式、設定項目の宣言方式、旧Gemini設定からの移行。
- 初回Ollama対応で提供する設定項目と接続テストの範囲。
- プロバイダーの登録時期とAnchorChainのロード順・依存指定。

既存Gemini設定の移行時には、キー、モデル、登録ID、メイン／サブの割り当てを維持する方針とする。保存ファイル名やスキーマ番号、具体的なクラス名はこの段階では固定しない。
