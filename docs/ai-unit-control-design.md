# AIによるユニット操作の設計メモ

作成・更新日：2026年10月22日（JST）。ユーザーとの議論に使う設計メモ。以下では、議論で整理した方針、現行実装で確認した事実、具体化前の設計提案、未調査事項を分ける。今回の実装は予約の作成・登録と登録結果の返却までとし、実行状況の監視・完了通知・完了後の再相談は将来の拡張とする。将来のリアルタイム操作へ拡張できる構成を目指す。具体的な契約・実装手順は検討中。設計書は責務と合意事項を共有するためのもので、型名・JSONの項目名・クラス構成は実装時の検証に合わせて見直せる。

関連する既存設計は[AIプロバイダーと相談実行方式](ai-provider-design.md)、現行の拡張契約は[公開APIガイド](public-api.md)を参照する。現時点では、操作カタログのオンデマンド取得、通常相談からの操作提案、ユーザー承認と予約登録を実装し、AI経由のソノブイ予約がゲームで動作することを確認した。複数案の一括提出・選択・承認と、案ごとのマッププレビューを実装する。第三者向け操作登録SDKは未公開。複数案の実モデルでの生成・実ゲームUIは今回の実装後に確認する。直近の議論で整理した複数案と共通マップ操作APIの方針は第15・16節に記す。

## 1. ユーザーの目標

将来的に、AI AdvisorがAIの指示を受けてゲーム内ユニットを操作できるようにする。直近の目標は、対潜哨戒ヘリをバッジで指定し、「カリフォルニアの進路に対潜哨戒網を作成して」と依頼すると、移動とソノブイ投下の操作予約をAIが作成し、MODがゲームへ登録できること。登録後の予約に沿った実行はゲームが担当する。

- 対象の艦や使用するユニットが指定されていない場合は、AIが問い返し、ユーザーが答えて依頼を具体化できると便利。
- 個別機能を場当たり的に追加するのではなく、操作のための基盤を整備したい。
- 公式更新や追加MODによってユニット・装備・センサー・施設・編隊・独自システムなどが増えることも考慮したい。拡張対象を兵器や特定の兵科に限定しない。
- 全体を同時に実装せず、調査と実装を順序立てて進めたい。

議論で整理した方針：

- ユーザーの意図の解釈、操作依頼かどうかの判断、不足条件の質問、計画はAIが担当する。MODが自然文を分類して操作専用の対話へ振り分ける構成は極力避ける。
- 今回の目標は、すべて予約操作で実現する。継続的に戦況を監視してAIが即時操作を繰り返す機能は、今回の実装範囲に含めない。
- 共通の操作基盤は予約専用に固定せず、将来のリアルタイム操作へ拡張できる構成にする。
- MODは構造化された操作要求の検証・ゲームへの登録・登録結果を扱う。会話の目的や未確認条件を理解する独自の管理機構は、必須にしない。
- 外部開発者が操作機能を追加できる仕組みを設ける。本体が追加MODの独自操作すべてを実装する必要はなく、外部開発者が説明・適用条件・検証・実行処理を提供できることを目指す。
- 将来はAIが適したユニットへ操作を割り振り、必要なら搭載機の準備・発艦を要求してから哨戒予約を作れることを目指す。
- 将来の拡張として、待機中に戦況が変わる場合に備え、操作完了を契機にAIへ再相談できる仕組みを設計に含める。操作実装はAIに依存しない結果を通知し、本体が必要な再相談要求を待機列で受け付ける。最新情報は実際の相談開始時に取得する。

「適切な哨戒網」の具体的な基準とAIに任せる判断範囲は引き続き検討する。承認・失効の基本方針は第13節、複数案の提出・選択は第15節に従う。

## 3. 対話の文脈と操作結果の分担

相談は、ユーザーの1回の入力からAIの回答までを指す。相談中に複数のAPI要求や情報取得が発生することがある。AIの問い返しにユーザーが答えることは、現行の会話履歴を使って行える。

依頼の目的、対象の選択、未確認条件、計画の検討は、AIとユーザーの対話で扱う。MODは「この質問は操作の質問だ」と判定せず、通常の相談としてメッセージをAIへ渡す。操作用のツール呼び出しなど、構造化された要求が届いたときに操作を処理する。

例として、次のような対話を想定する。問い返す順番や文面を固定する意図はない。

1. ユーザー：「進路に対潜哨戒網を作成して」
2. アドバイザー：「どの艦の進路ですか？」
3. ユーザー：カリフォルニアを指定。
4. アドバイザー：必要に応じて使用するヘリなどを確認し、移動と投下の予約案を作成する。
5. MOD：構造化された要求を検証して提案を保留し、ユーザーの承認時に最新状態を再検証して予約を登録する。
6. ゲーム：登録された予約に従って移動・投下する。

初稿では、依頼の目的・未確認条件・計画・実行状況をまとめてMODが保持する案を提示した。その後の議論で、対話の意味を管理する役割と、実際の操作を管理する役割を分離した。目的や未確認条件をMODが理解して管理することは、今回の必須要件にしない。

MODが扱うのは、登録要求の対象と引数、受付・拒否、登録した命令の識別などの実行に関する事実。ゲームから実行状況を取得する場合も、対話の目的とは独立した操作の状態として扱う。

将来の再相談では、AIが作成した依頼の続きの文章と対象参照を、特定の操作の完了へ結び付けて再相談管理が保持する。この保持は文章の意味を解釈する作業管理ではなく、「この操作が完了したら、この内容と実結果を相談実行部へ渡す」という機械的な対応として扱う。操作実装は再相談の文章やAIの通信を扱わず、操作の状態・結果だけを本体へ返す。詳細は第7節を参照する。

履歴の送信数によって過去の確認事項が失われる問題は、対話の継続方法として別途検討する。それを理由に、MODへ自然文の意図を理解する作業管理機構を導入しない。不足条件をユーザーへ質問するか、AIが候補を選べるようにするかは、委任する範囲と併せて今後検討する。

## 4. 操作基盤の責務と拡張方針

| 担当 | 責務 |
| --- | --- |
| AI | 依頼の解釈、必要な情報の選択、不足条件の質問、対象選定、計画と構造化された操作要求の作成 |
| 相談実行部 | メッセージ・取得情報・操作要求と結果をAI接続へ受け渡し、手動相談や再相談要求を受け付けて実行する |
| 操作カタログ | 内蔵・外部操作の登録と発見、説明・引数・適用条件などの情報を提供し、対応対象の照会を登録実装へ委譲する |
| 操作の受付・実行 | 共通の要求検証、登録された操作実装の呼び出し、受付・状態・結果の受領と通知、重複登録の防止 |
| 提案管理・承認UI | 案の識別と保持、コマンドが宣言した提案数の検証と選択方式の制御、案の表示・選択・承認、未承認提案の失効 |
| 共通マップ操作API | コマンドから指定された点・線・円の一時描画と中央移動を提供し、プレビューごとの描画と後片付けを管理する |
| 再相談の管理 | 操作完了と再相談内容の対応付け、再相談要求の待機列への登録、相談実行部への受け渡し |
| 内蔵・外部の操作実装 | 操作の説明・引数・適用条件・提案数の制約・選択方式、操作固有の検証、プレビュー内容の指定、ゲームや追加MODへの命令発行。提供できる操作の状態・完了・失敗と結果を本体へ返す |
| ゲーム接続（各操作実装側） | 現在の操作対象を解決し、ゲーム側の機能を呼び出して結果を取得する。内蔵操作は補助処理を共有でき、外部操作は独自の接続処理を持てる |
| ゲーム | 今回登録した予約に従った移動・投下などの実行 |

上表は将来の拡張を含む責務分離案。今回の操作結果は予約の登録成否を扱い、実行状況の監視・完了通知と再相談の管理は後段で実装する。

「共通の操作管理」という区分の内部を、操作カタログ、操作の受付・実行、再相談の管理へ分ける。これは変更理由と依存先を分けるための責務境界であり、各項目を必ず大きなクラス群に分ける指定ではない。具体的な型や公開インターフェースは未決定。

ゲーム接続も、すべての操作に必須の一個の共通アダプターとしては扱わない。各操作実装が自分の依存先に応じて持つ責務とし、共有できる部分だけを再利用する。

共通のゲーム連携部品は予約情報などの用途ごとに分け、各操作が必要な部品だけを使う。読み取りと予約の追加・削除は分離し、取得結果には座標などの値だけを保持する。操作固有のインターフェース、ゲーム内部の予約オブジェクト、UI部品を共通の読み取り契約へ持ち込まない。追記・置換などの操作方針は各コマンドが決める。今回切り出すのは予約経路の読み取りだけであり、未使用の機能や必須の継承構造、外部公開SDKは追加しない。

現行の情報取得窓口は読み取り専用の責務を維持し、操作の窓口を別に設ける案を推奨する。情報取得を呼び出しただけでゲームの状態が変わる構成にはしない。

AIからは、操作名・対象・引数などを構造化された情報として受け取る。自然言語の回答から「投下した」「移動せよ」といった文言を探して実行する方式は採らない。具体的な形式・型名・公開APIは未決定。

### 予約操作とリアルタイム操作の拡張性

今回実装するのは予約操作の作成・登録だが、共通の操作契約を「予約列を作ること」だけに固定しない。次の責務を分け、予約列をその基盤の利用方式の一つとして扱う。

| 要素 | 設計上の役割 |
| --- | --- |
| 操作の定義 | 移動・投下などの操作、対象、引数を表す |
| 検証と実行 | 現在の対象・能力を確認し、ゲームへ命令を渡す |
| 実行方式 | 今回はゲームへの予約登録。将来は即時の命令発行にも対応する |
| 状態取得 | AIが判断に使う情報と予約の登録結果を取得する。実行状況の監視は将来の拡張とする |

将来のリアルタイム操作では、最新情報の継続取得、命令の中断・差し替え、AIによる判断の繰り返しが必要になる。それらを追加できる責務境界を用意し、具体的な制御機構の実装は後段に回す。現行の相談スナップショットの寿命と、将来の継続的な状態取得は分けて検討する。個々の外部操作へ、最初から予約登録と即時発行の両方を実装する義務は設けない案とする。

操作完了などの節目で新しい相談を開始する方式は、常時リアルタイムに判断・操作を繰り返す方式とは区別する。予約の実行はゲームへ任せたまま、必要な節目で最新情報を取得して次の予約を計画できる。

### プロバイダーとの境界

共通化するのは操作の意味と検証・実行の境界。プロバイダー固有のツール形式、通信回数、計画の生成手順は各実装側へ残す。既存の独自プロバイダーにも新しい通信手順を一律に強制せず、操作に未対応の実装は従来の助言機能を維持できる構成を検討する。

操作機能の登録口は、AIプロバイダーの登録口とは分ける案とする。AIとの通信を担当する拡張と、ゲームや追加MODへの操作を担当する拡張では、依存先と実行するスレッドが異なる。既存のAIプロバイダーを利用しながら、別の外部MODが操作だけを追加できる構成を目指す。

予約操作でも将来のリアルタイム操作でも、ユーザーの文章を解釈するのはAI、構造化された操作要求を検証・処理するのはMOD、という分担を維持する。

## 5. 今回の予約操作で検討する事項

### WIP設定による有効化

当面は試験的な機能として提供し、設定に次のカテゴリとチェックボックスを追加する。

- カテゴリ：**WIP（試験的機能）**
- 項目：**ユニット操作の予約を有効にする**
- 初期値：**OFF**

OFF時は、AIへの操作機能の提示と、MOD側の新規予約登録の受付を無効にする。UIやAIへの提示だけで制御せず、予約登録の共通受付でも有効状態を確認する。OFFへ変更した後に操作要求が届いた場合も、新規予約は登録しない。

OFFに戻しても、既にゲームへ登録した予約は維持する。機能の有効化と、登録済み予約の取消しは別の操作として扱う。

### 対象と最新状態

初期対象である発艦済みヘリへの予約登録では、対象が現在も存在し、プレイヤーが操作でき、要求された予約を登録できる能力・装備を持つことを確認する。相談開始時の情報だけで、登録時の可否を確定しない。

将来の拡張では搭載機や操作結果として生成される対象も扱うため、すべての操作要求に既存のマップ上ユニットIDを必須とする契約には固定しない。搭載中の候補、生成待ちの参照、生成済みのユニットを区別し、具体的な対象の解決・検証方法は操作に応じて定義する。

予約した操作の実行時には、装備の残量などが変化している可能性がある。登録時に検証する条件と、実行時にゲーム側が判定する条件を調査し、予約の登録を将来の実行成功の保証とは扱わない。

ユニット参照は進行中のミッションに結び付ける。セーブの読み込みや別ミッションへの移動後に、古い要求の参照が別ユニットへ結び付かないようにする。参照の寿命と失効条件は設計時に具体化する。

### 予約の表現と既存命令

移動と投下の操作を、対象・引数・順序が分かる予約案として受け渡す。既存の予約へ追加するか、置き換えるかは、ユーザーへの提供方法も含めて未決定。

今回の実行方式は、ゲーム標準の予約命令を組み立てて登録することを前提とする。登録後の移動と投下はゲームへ任せ、AIとの通信を開き続けて完了を待つ構成や、MOD独自の長時間の作業実行機構を必須にしない。1地点での投下は、移動を内包したゲーム標準の予約を利用する経路を確認した（第10節）。この内部表現に合わせて、共通操作契約でも移動と投下を必ず別々の要求に分ける必要はない。

ゲームオブジェクトへの操作は、ゲーム側の実行スレッドへ受け渡す。通信処理のバックグラウンドから直接操作しない。

### 登録結果と重複登録

再試行やサブ接続への切り替えによって、同じ移動・投下の予約が二重に登録されないよう、登録要求と結果を本体側で識別する案とする。具体的な識別方法は未決定。

予約の登録成功と、実際の移動・投下の完了を区別する。登録できた時点では予約を登録した結果を返し、「哨戒網を作成した」とは報告しない。予約列の一部だけが登録された場合に、どの部分まで受け付けられたかを扱えるようにする。

予約の取得・変更・取消しをどこまで提供するかは未決定。相談の中止、予約の取消し、会話履歴の消去、ユーザー自身による命令変更も、それぞれの効果を区別する。投下済みのソノブイを元へ戻せることは前提にしない。

## 6. 外部開発者による操作機能の拡張

### 基盤の対応範囲

本体の責務は、外部の操作を登録・発見し、その情報をAIへ提供して、構造化された要求を適切な実装へ渡し、結果を返せる仕組みを用意すること。追加MODの独自操作を、本体の開発者がすべて実装する必要はない。

操作固有の用途、適用条件、ゲーム内部や追加MODの呼び出し方は、対応する外部実装が提供する。本体が個々の操作の戦術的な意味や内部処理を理解して振り分ける構成にはしない。操作実装が返す結果はAIへの再相談から独立させ、本体側で画面への通知や再相談などへ利用できる契約を目指す。

### 操作ごとの実装を組み合わせる案

現時点の推奨案は、移動・ソノブイ投下などの操作ごとに実装を登録し、対象の能力に応じて組み合わせる構成。兵科をまたいで共有される操作と、同じ機種でも異なる搭載装備を扱いやすくする。

検討した構成の評価は次のとおり。具体的な型名・インターフェース・クラス構成は未決定。

| 構成 | 評価 |
| --- | --- |
| 機種・艦級ごとのアダプター | 固有の事情に対応する用途には有効。ただし共通する操作の重複に注意が必要 |
| 対潜ヘリなどの基底クラスからの継承 | 同種の実装を共有する用途には有効。ただし兵科をまたぐ能力や装備差を継承だけで表す構成は複雑になりやすい |
| 操作ごとの実装を登録して組み合わせる | 能力の共有と追加に向いており、共通基盤の中心として推奨 |

外部開発者が自分の実装内で基底クラスやユニット固有のアダプターを使うことは制限しない。本体への登録に特定の兵科の継承を要求しない案とする。

### 外部実装が提供する情報と処理

- AIへ提示する操作の説明。未知の操作でも用途を判断できるよう、何をする機能かを伝える。
- 必要な引数と、その形式。
- 適用できる対象や装備を判定する仕組み。
- 操作固有の引数・状態の検証。
- ゲームや追加MODへ予約などの命令を渡す実装と、その結果。
- 実際の完了を提供できる場合は、予約の登録とは別の完了判定と、生成された対象などの結果。AIへの再相談の文章や通信処理は操作実装に要求しない。

本体が行う共通の受付・検証と、外部実装が行う操作固有の検証を分ける。特定の兵器や機種の知識を、本体側の固定分岐へ追加し続ける構成は避ける。実行完了の取得が未対応の操作について、受付・登録結果を実行完了へ置き換えない。

### AIによる操作とユニットの選定

以下は今後の情報提供・問い合わせの構成案。現時点で、この操作カタログや問い合わせを実装済みという意味ではない。

1. 本体同梱と外部登録を含む、利用可能な操作の説明をAIが参照する。
2. AIが依頼の達成に必要な操作を判断する。例えば、哨戒網の作成に移動とソノブイ投下を使うと判断する。
3. AIがその操作に対応する対象を問い合わせ、登録された適用条件に基づく候補を取得する。
4. AIが位置、搭載数、燃料、現在の予約などの必要な情報を取得し、目的に合う対象を選ぶ。
5. AIが対象と引数を指定して操作要求を出し、本体と操作実装が登録時の条件を確認して処理する。

「この操作に対応する」という事実を返すのは本体と操作実装、「今回どれを使うとよいか」を判断するのはAI。バッジで対象が指定されている場合は、その指定を基に計画する。未指定の場合にAIが選ぶかユーザーへ確認するかは、委任範囲の設計で決める。

将来は発艦済みのユニットだけでなく、搭載機なども選定候補に含める。必要な準備・発艦を選ぶのはAIであり、本体が対潜任務のための発艦を自動判断する構成にはしない。

機能としての対応と、現在その要求を受け付けられるかは分ける。候補を取得した後にも状況が変化し得るため、候補一覧を取得できたことだけで登録成功を保証しない。操作名やIDだけでは未知の操作の用途は分からないため、外部登録された操作も説明と必要な情報をAIへ提供できる必要がある。

### 兵器以外も含めた追加要素

拡張の単位は、操作対象と、その対象に対して実行できる機能とする。対象や追加要素には、ユニット、装備、センサー、施設、編隊、独自システムなどがあり得る。実際に提供できる操作は、それぞれの実装とゲーム側の機能による。

- 既存の操作方式を使う追加要素は、既存の操作実装で扱えることを目指す。例えば通常の投下機能を使う追加ソノブイは、名称ごとに専用実装を作らず、搭載物・操作機能から判定して既存処理へ装備を指定する。利用できる判定経路は未調査。
- 新しい操作方式を持つ要素は、外部開発者が操作の説明・引数・適用条件・検証・実行処理を追加して扱えるようにする。
- 機能や呼び出し経路を取得できず、対応する操作実装もない独自要素は、自動操作には対応できない。AIが名前から機能や実行方法を推測することに依存しない。

今回実装する対象は対潜ヘリに必要な範囲に絞りつつ、拡張契約を兵器の使用や特定の兵科に固定しない。未知の追加機能すべてを自動理解することは目標にしない。

### 内蔵機能でも同じ登録口を利用する案

本体同梱の移動・ソノブイ投下も、外部拡張と同じ登録口を使う案を推奨する。今回の機能をその仕組みで実装することで、外部開発者が操作を追加するために必要な情報・呼び出し・結果の受け渡しが足りているかを確認する。

操作の内部設計と、第三者へ公開する契約は分けて検討する。初期実装で未検証のインターフェースを公開仕様として固定する必要はない。

## 7. 将来の発艦と、操作完了時のAIへの再相談

### 発艦前の候補と生成後の操作対象

将来的には、「カリフォルニアの進路に対潜哨戒網を作成して」という依頼に対し、AIが適したユニットを選び、必要なら搭載機の準備・発艦を要求し、その結果を使って哨戒予約を作ることを目指す。

発艦前の搭載機は選定候補になっても、その時点で操作可能なマップ上の機体とは限らない。発艦によって生成された機体は、発艦要求に対応する結果として識別し、後続の相談や操作へ渡せるようにする案とする。名前や新たな機体の出現だけで対応を推測せず、要求と生成結果をどう結び付けられるか調査する。

操作の結果として得られる対象を、後続の操作へ受け渡せる契約が必要。初期実装は発艦済みヘリに絞るが、その前提を共通の操作契約へ固定しない。

### 長時間の待機と位置の有効性

準備・発艦にゲーム内時間で30分や1時間かかる場合、その間に対象艦が進み、最初に決めた投下地点が艦の後方になり得る。生成された機体を特定するだけでは、この問題は解決しない。

対処案として、対象艦の進路上の前方などの相対的な指定を後から位置へ具体化する方式と、発艦完了などの節目でAIへ最新情報を渡し、再計画する方式を検討した。相対位置の具体化だけでは、敵の状況や任務自体の変化までは判断できない。準備時間と移動の予測によって最初に座標を決める方式もあり得るが、その後の針路変更などを考えると予測だけには依存しない。

今回の議論では、発艦完了後に最新の状況からAIが計画し直す方式を、将来目標に合う案として整理した。操作要求を受け付けた時点で、すべての後続操作の対象・座標が確定していることを共通契約の前提にしない。

### 操作完了をきっかけに再相談する流れ

1. AIがヘリの準備・発艦を要求し、必要な操作の完了後に再相談するための文章と対象参照を併せて渡す。
2. 操作の受付・実行が登録実装へ要求を渡す。再相談の管理は、その操作と再相談内容の対応を保持する。
3. 操作実装がゲームへ予約を登録し、受付・登録結果を本体へ返す。ゲームがその予約を実行する。
4. 操作実装が実際の完了を判定し、生成された機体などの結果を本体へ返す。操作実装からAIは呼び出さない。
5. 再相談の管理が、完了結果に対応する再相談要求を待機列へ入れる。この時点で、後で使う最新戦況を固定しない。
6. 相談実行部が実行できる時点で要求を受け取り、その時点のゲーム情報を新たに取得する。保持した文章・対象参照・実際の操作結果とともに新しい相談を開始する。
7. AIが最新の状況を確認し、利用可能になったヘリを使う哨戒網を再計画して、移動・投下の予約を要求する。

AIが残す文章の例：

> 発艦したヘリを使用し、カリフォルニアの最新の進路に対潜哨戒網を作成してください。最新状況を確認して計画してください。

この文章は依頼の続きとして扱い、実際の発艦結果は操作実装から受け取ったものを使い、現在位置などの戦況は実際の再相談開始時に取得して添える。完了結果が示す時点と最新戦況の時点を区別する。対象艦の参照も保持し、名前だけで再特定することに依存しない。過去の相談内IDやスナップショットを、そのまま現在の対象や戦況として再利用しない。

前のAI応答後も長時間のHTTP通信を開き続ける必要はない。操作完了を契機に別の相談を要求し、その相談を実行する時点の情報で計画する。最初に描いた計画を必ず継続させるのではなく、最新状況を評価する判断はAIに任せる。

### 操作結果と再相談の契約を分離する

操作実装は、受付・登録結果、実際の完了・失敗など提供できる状態と結果を本体へ返す。再相談するか、画面へ通知するだけかなどの利用方法は本体側が担当する。「AIへ完了を返す操作実装」ではなく、操作結果を提供する実装に本体が必要な再相談を結び付ける構成とする。

AIが操作要求と再相談の登録を一度に送る表現を採用しても、両者の責務は分ける。操作実装に再相談の文章を渡したり、特定プロバイダーの通信や会話履歴を扱わせたりする必要はない。

発艦では「予約を登録できたこと」と「機体が出現し、操作可能になったこと」を区別する。操作実装は後者の完了と生成対象を結果として提供し、その結果へ再相談管理が次の相談を結び付ける。外部追加操作にも同じ結果通知の仕組みを利用できる構成を目指す。

### 再相談要求の順次処理

操作完了時にユーザーが別の相談をしている可能性があるため、完了通知の処理から直接、新しいAI通信を始めない。再相談の管理は要求を待機列で受け付け、相談実行部が実行できる時点で受け渡す。既存の相談を並列化することを、この機能の前提にはしない。

最新戦況の取得は、完了通知の受領時や待機列への登録時ではなく、相談実行部が実際にその再相談を開始する時点で行う。完了時に新しい情報を取得しても、相談の待機中に再び古くなる可能性があるため。手動相談と再相談の優先順位、複数の完了通知がある場合の処理順などの詳細は未決定。

同じ完了結果による二重の再相談を防ぐ扱いは、再相談の管理側で検討する。操作が失敗・取消しになった場合、対象が消失した場合、ミッションが変わった場合の再相談の扱いは未決定。ゲーム側の完了通知または状態確認の経路も未調査。

この仕組みは、ゲームが予約を実行し、その節目でAIが次の予約を計画するためのもの。常時リアルタイム操作を今回の実装に加える意味ではない。準備・発艦と完了時の再相談の実装は後段の課題とし、操作結果の提供と相談の受付を独立させる拡張性を初期の基盤設計で考慮する。

## 8. 調査・実装を進める順序の案

| 段階 | 内容 | 確認する到達点 |
| --- | --- | --- |
| 1. ゲーム側の調査 | 移動とソノブイ投下の予約列を、MODから構築・登録できるか調べる。既存予約との関係、登録結果、取得・変更・取消しの経路も確認する | 利用できる予約機能と、その制約が説明できる |
| 2. 最小の操作基盤 | 操作カタログ、受付・実行、各実装側のゲーム接続と登録結果の返却を分離する | 内蔵の移動・投下も同じ登録口で扱え、AI非依存の登録結果を返せる。将来の完了通知を追加できる境界を維持する |
| 3. AIなしで予約を確認 | 指定ヘリの「指定地点へ移動→ソノブイ1発投下」を予約として登録する | 登録結果と、ゲームによる実際の移動・投下を確認できる |

| 6. 後段の発艦・再相談 | 搭載機の準備・発艦と生成対象の受け渡し、操作結果に対応する再相談の管理と順次処理を追加する | 登録と実際の完了を区別し、再相談を実際に開始する時点の最新情報でAIが計画できる |

全体の設計を先に整理し、最初の実行対象は「発艦済みの指定ヘリ・指定地点・1発の投下を予約すること」までに絞る案。生成待ちの対象・操作結果の受け渡し・完了時の再相談と、リアルタイム操作への拡張性は初期設計に含め、実装は段階的に進める。今回の予約操作と、後段の準備・発艦からの再相談を区別する。

### 次に進める順序

既存の単一提案・承認を出発点として、次の順で進める案とする。

1. 共通マップ操作APIを整備する。点・線・円・中央移動と、承認画面に対応する一時描画の寿命を扱う。
2. 現行の1案の承認に位置プレビューを接続する。実行予定の引数と表示位置が一致し、画面を閉じると描画が消えることを実ゲームで確認する。
3. 複数案の管理、提案数の宣言・検証、選択・承認UI、AIへ渡すツール定義と短い指示を整える。単一案で確認したマップ機能を再利用する。

2026-10-22時点で1・2の内部実装と模擬試験まで完了。実ゲームでの位置・描画・後片付けの確認を先に行う。詳細は第15・16節。単一提案での確認を先に行うが、マップ操作APIの責務をソノブイや1案専用に固定しない。

各段階の試験は、その段階で追加した動作に合わせる。実ゲームで移動・投下を確認するのは、登録した予約が正しく機能するかを検証する試験であり、製品に自動監視や完了通知を実装する意味ではない。予約の登録とゲームによる実行が成立するかの確認と、AIの計画が戦術的に有用かの評価は分ける。モデルの判断の誤りを、直ちに通信や命令発行の不具合とは扱わない。

## 10. 発艦済みヘリの移動・ソノブイ1発投下の調査

調査対象DLLのSHA256は`c913e31f2d73e526f2d28043f522f2be26f12534fd0421eedee3cd70eab9cdd8`。再開用のIL抜粋・対象ファイルのハッシュはローカル専用の`artifacts/sonobuoy-reservation-research/2026-10-21/`に保存し、Git・配布物へ含めない。

### 結論と標準処理

**ゲーム標準の予約を利用して実現できる見込みが高い。** ヘリをMODが毎フレーム誘導し、到着後に独自処理でソノブイを生成する必要はない。

標準UIの`SonobuoyLineState.OffsetAttack`は、公開メソッド`ObjectBase.SetAttackAtWaypointTask`を呼び、`AttackAtWaypoint`を登録する。この型は`GoToWaypointTask`を継承し、地点への移動と、その近傍で投下処理を開始する予約を一つにまとめている。`AttackWaypointViewModel`も生成され、ゲーム標準の予約表示・経路シミュレーションへ接続される。

標準の処理経路は次のとおり。

1. `SetAttackAtWaypointTask`で対象機体・弾薬・地点・数量を指定する。
2. `UserRootNode.AddTask`へ予約が登録され、ゲームが移動を実行する。
3. `AttackAtWaypoint.OnUpdate`が地点への接近を判定し、`SingleAttack`から数量付きの`EngageTask`を作る。
4. ゲームの武器システムが投下を実行し、`Bomb.Container_Launch`へ進む。
5. ソノブイはその後、`Bomb.DeploySonobuoy`で展開される。

`DropSonobuoyTask`という別の型も存在するが、調査した地点指定UIの登録経路は上記だった。単にこの型を呼ぶ構成を推奨する根拠にはしない。

### 1地点・1機・1発に必要な指定と検証

`SetAttackAtWaypointTask`の主要な指定は次のとおり。これは実装候補であり、共通APIの確定仕様ではない。

| 引数 | 初期試作での扱い |
| --- | --- |
| 呼び出し対象 | 発艦済みの指定ヘリの`ObjectBase` |
| `ammunitionName` | 実際の搭載弾薬から取得した内部キー。表示名や特定機種名で固定しない |
| `targetObject` | `null`。敵ユニットを攻撃対象として指定する操作ではない |
| `targetGeoPosition` / `waypointGeoPosition` | 同じ指定地点を渡す。経路と投下目標を別々の場所へ設定しない |
| `salvo` | `1`。標準UIのソノブイ予約も1を渡す |
| `after` | 末尾追加なら`null`。既存予約の直後へ入れる場合はその予約を指定 |
| `salvoType` / `areaRadius` | 標準UIと同じ`PerLauncher` / `-1`が出発点 |
| `formationAttack` | 初期試作では`false`を推奨。標準UIの既定値は`true`で、編隊の他機を追加する分岐がある |
| `attackOnlyDetected` | 標準UIと同じ`false`。今回の地点投下は探知した敵を必要としない |

機体が存在すること、プレイヤーの操作対象であること、発艦済みであること、投下可能なソノブイと未使用の残数があること、座標が有効であることは操作実装側で確認する。予約生成メソッドは、これらを一括して保証する検証口ではない。`_userRoot`や弾薬がない場合などには`null`を返すため、戻り値だけでなく登録列へ入ったことも確認する。

標準UIは残数から、同じ弾薬の既存投下予約・待機中の`EngageTask`・武器システムで処理中の投下分を引いている。単純な搭載残数だけを、追加予約できる残数としない。

高度はゲームが弾薬の投下高度範囲から補正する。ただし予約生成時の経路高度は、機体の現在高度やUIで選択された予約の高度を参照する。渡した座標の高さだけで任意の飛行高度を設定できるとは扱わず、実装時はUI選択の影響も確認する。

投下の開始位置はゲームの到達許容範囲・速度・高度などで決まり、座標への完全一致後に静止して投下する処理ではない。「指定地点付近へ投下する予約」として扱う。

### 既存予約、取得・変更・取消し

| 操作 | 確認できた経路と注意点 |
| --- | --- |
| 末尾追加 | `after=null`は`AddTask(task)`となり、既存列へ追加する。工場メソッド自体は既存経路を消さない |
| 途中挿入 | `AddTask(task, after)`は指定予約の直後へ挿入する。存在しない`after`の場合は追加されない経路があるため、戻りオブジェクトの存在だけで登録成功としない |
| 置き換え | 標準UIの非追加操作は、現在命令の解除や編隊からの個別行動への切替、`RemoveWaypoints`を組み合わせる。予約の追加だけで現在の行動をすべて上書きできるとは扱わない |
| 予約取得 | `_userRoot.TaskViewModels`から予約の実体を参照できる。`ExportWaypoints`は移動に加え弾薬・数量・攻撃座標なども出力する |
| 変更 | `GoToWaypointTask.UpdatePosition`、`AttackAtWaypoint.UpdateSalvoAmount`等がある。標準UIと同じ派生状態・シミュレーション更新まで含む変更手順は実装時に確認する |
| 個別削除 | `UserRootNode.DeleteTask(task)`が予約ノードと表示を削除し、経路シミュレーションを更新する |
| 全削除 | `ObjectBase.RemoveWaypoints`から`UserRootNode.ClearTasks`へ進む。ユーザーが作った他の予約も消えるため、AIの予約だけの取消しに使わない |

初期試作は、既存予約がない機体で1件を確認した後、末尾追加を検証する案を推奨する。追加・置き換えの製品仕様は引き続き未決定。

予約が既に投下処理を発行した後は、予約ノードの削除と、武器システムの処理取消しは別になる。投下前・投下処理への引き渡し後・実投下後で取消しの意味を区別し、一律に「予約削除で投下を中止できる」とは報告しない。

### 将来の完了通知に向けた調査記録

以下は将来の完了通知を検討するための参考情報。今回は予約登録の成否だけを返し、移動・投下・展開の完了判定や生成物との対応付けは実装しない。

| 段階 | 確認できた状態・意味 |
| --- | --- |
| 予約登録 | 予約オブジェクトが機体の命令列へ入ったこと。移動・投下の成功を意味しない |
| 予約の到達・処理終了 | `AttackAtWaypoint`は投下用`EngageTask`の作成後、移動予約を完了扱いにする。`ReachedWaypoint`や`RemovedOrFinished`を実投下成功の通知として使わない。後者は中断時にも呼ばれる |
| 実際の投下・展開 | `Bomb.Container_Launch`が投下側の経路。展開後は公開の`Bomb.Deployed.Value`が`true`になる |

実投下・展開の判定に使える処理と状態は存在する。ただし「自分が登録した予約」と「その予約により投下されたソノブイ」の厳密な対応付けは、今回の静的調査だけでは確定していない。発射元・弾薬・武器システム・生成物を対応付ける方法は、完了通知を実装する段階で検証する。弾薬数の減少だけでは、ユーザーによる別の投下と区別できない場合がある。

### 追加MODと、実ゲームで残る確認

ソノブイは実行時の弾薬分類で判別できる。調査した処理は`Bomb`系の弾薬と`Sonobuoy`の副分類を使用し、機種名・ソノブイ名の固定リストを要求していない。標準の搭載・投下方式を使う追加MODにも同じ操作実装を適用できる見込み。独自の投下方式は従来の設計どおり外部実装で追加する。

なお、武器システムには弾薬別の`SalvoFireAmount`があり、ソノブイについては未指定時に1発とする経路を確認した。「予約の`salvo=1`なら、どの独自設定でも必ず実投下1発」とまでは断定しない。実際の対象機体・搭載品で、投下数と生成物を確認する。

次の実装・実ゲーム確認は、AI通信なしで行う最小試作が適切。試作が返す結果は予約登録の成否までとし、移動・投下・展開は実画面で確認する。

1. 発艦済みで経路が空の指定ヘリに、指定地点への1発投下予約を登録する。
2. ゲーム標準の経路表示、移動、投下1発、残弾減少、ソノブイの展開を確認する。
3. 既存経路への末尾追加と、投下開始前の個別取消しを確認する。
4. 編隊所属機でも指定した1機だけが動作するか、高度・速度・現在命令がどう影響するか確認する。

今回の調査から独自の移動制御機構を追加する必要は見つかっていない。共通の操作カタログ・受付と、ゲーム固有の予約実装を分ける方針を維持し、ゲーム標準の複合予約を扱える形で最小試作へ進める。

## 11. AIなしの最小試作

WIP設定と、操作の登録・候補取得・要求受付・登録結果の返却を実装した。現在の起動口は[開発用ローカルAPI](developer-local-api.md#wip-native-order-trial-no-ai)と[既存CLIのoperationsサブコマンド](../tools/advisor-dev.md#wip-operation-trial)。この開発用APIは調査用の暫定入口であり、安定した公開仕様や将来の操作APIとの形式互換性を保証する対象ではない。この段階ではAIへ操作を提示せずに検証した。続くAI接続の設計と実装範囲は第12節に記載する。

最小の内部契約は、操作ID・説明と引数形式・候補取得・実行という登録実装で構成する。初期から公開APIの型群へ固定せず、既存公開APIのバージョンは維持する。内蔵のソノブイ操作もこの共通受付を利用する。

共通受付はWIP設定とゲームスレッドを確認し、ロードした戦闘に結び付いたscope_id、要求ID、操作と引数を受け取る。ゲーム固有の機体・装備・登録可否は各操作実装が担当する。受付と予約登録は同期的にゲームスレッドで完了させ、HTTPワーカーから直接ゲームオブジェクトを操作しない。

ソノブイ試作は指定機への末尾追加・1発に限定する。現在のプレイヤーTaskforceObjectsから機体を取り直し、登録直前に操作可否・発艦状態・現在命令・既存予約を差し引いた残数・1発投下に対応する装備設定を確認する。追従中や競合する命令がある場合は理由付きで拒否し、勝手に編隊や既存命令を変更しない。ゲーム標準のSetAttackAtWaypointTaskをformationAttack=falseで呼び、戻り値だけでなく予約列への追加も確認する。

同じ要求ID・同じ内容の再送は記録した結果を返す。引数変更や古い戦闘scopeは拒否する。予期しない例外を通常の拒否へ変換せず、結果不明の要求として同じIDの再実行を止める。記録は戦闘単位のメモリに保持し、上限時は古い結果を捨てず新規要求を拒否する。

初期リリースでは深度を変更せず、ユーザーがゲームで選択済みの設定をそのまま利用する。深度は候補と登録結果の`depth`へ`above_layer`（変温層より上）／`below_layer`（下）／`alternating`（ゲームの断続放射）として返す読み取り専用情報とする。将来の明示的な深度選択を追加できる形は残すが、初期版の操作定義には深度変更引数を公開しない。

AI等から予約要求の`arguments.depth`が渡されても、この版では値を解釈・適用せず無視して、その他の正常な予約を登録する。未対応の別引数や座標・弾薬等の不正値を一般的に無視する設計にはしない。候補取得時の深度を保持して書き戻さず、登録時に対象ヘリの最新の設定を読み直して結果へ返す。これによりAIとの往復中にユーザーが選択した設定を上書きしない。実際の投下にはゲーム標準の処理がその時点のヘリの設定を使用する。

標準ゲームの深度はヘリ単位の共通設定で、そのヘリの既存予約を含む未実行の投下すべてに適用される。ユーザーが後から設定を変えた場合もそれを尊重する。登録結果は登録時点の観測値であり、予約ごとに固定された深度ではない。同じ要求IDの再送は元の結果を返し、設定の書き戻しや新しい予約を行わない。他のヘリを操作しない。

短い説明は既存battle.jsonのoperation_sonobuoy_dropへ置き、操作定義だけで使用する。専用のプロンプト管理機構、深度変更の無効化スイッチ、予約ごとの深度メタデータ、投下時の独自フックは追加しない。通常相談からの接続は第12節の独立した操作窓口を使う。

これは予約登録までの試作であり、進捗監視・実投下との対応付け・完了通知・自動再相談は実装しない。2026-10-21に深度を指定しないHobby 1の予約表示・移動・ソノブイ1発の実投下はユーザーが確認済み。続いて、要求にbelow_layerを指定してもalternatingを維持する登録を確認し、ユーザーが再生して移動・物理投下・断続放射設定の維持まで確認した。

## 12. 操作カタログのオンデマンド取得とAI接続

多数の内蔵・外部操作が登録されることを最初から前提にする。今回ソノブイ操作が1種類であっても、その定義を初期プロンプトへ直接埋め込む例外経路は作らない。標準エンジンは戦況用query_situationを提供し、WIPがONの相談では操作一覧・定義・候補・提案を用途別ツールで追加する。独立した読み取りは同じAI応答内でまとめて取得できる。独自相談処理は従来の戦況取得と操作サービスを直接利用でき、標準エンジンの取得方式を強制しない。

| action | 取得・処理する内容 |
| --- | --- |
| list | 登録操作のIDと短い説明。searchでID／説明を検索、offset／limitでページ取得する。個別の引数定義や候補を含めない |
| describe | operation_idで選んだ1操作の説明と引数定義 |
| candidates | operation_idに対応する現在の対象候補。target_refによる絞り込みとページ取得に対応 |
| submit | request_id・plansで全案と各案の操作列を一括提出し、承認待ちの受付結果を返す（第15節） |
| execute | 旧クライアント向けの単一案互換経路。operation_id・target_ref・request_id・argumentsで1操作ずつ保留する |

初期入力のサイズは登録操作数に比例しない。検索や定義取得は同じ登録口から行い、ソノブイ専用の分岐を通信側へ置かない。「どんな操作ができる？」には操作カタログ、「このヘリで何ができる？」には操作と候補の照会で答えられる構成にする。検索語はID／英語の説明へ部分一致する単純な方式で、自然文の意味解釈をMODへ追加しない。

操作カタログ・各実装の説明／引数／候補／実行処理、要求の受付とゲームスレッドへの受け渡し、プロバイダー固有のツール表現を分離する。操作説明は既存の外部プロンプトファイルで管理する。独自相談処理へ標準エンジンの通信往復を強制せず、任意のIAdvisorOperationsサービスから同じ窓口を利用可能にする。未対応の旧プロバイダーは従来の情報取得と助言を継続できる。

既存公開APIはコンストラクターと必須インターフェースを維持し、ConsultationInput.OperationToolJson、ConsultationContext.Operations、継続時のOperationsJsonを追加する。これはプロバイダー向けの任意サービスであり、操作実装の外部登録SDKを確定するものではない。操作拡張自体の公開契約は内部基盤とAI接続を検証してから整える。

WIPチェックは開発APIだけでなくAI経由の操作全体へ適用する。OFFでは操作窓口をAIへ提示せず、既に提示済みの相談から届く要求も共通受付で拒否する。開発APIの有効化はAI操作の利用条件にしない。WIP画面では現在対応する操作範囲を説明し、暫定的な検証入口やOFF時の細則を説明文に含めない。

情報取得は従来どおり相談開始時のスナップショット、操作の候補と登録はゲームスレッド上の最新状態を使用する。候補には現在位置・利用可能弾数・現在の深度を含め、予約直前にも操作可否を再検証する。敵の隠れた情報は参照しない。ソノブイ操作では候補取得と登録の両方で、自軍基本情報と弾薬情報の許可を再確認し、操作窓口による情報選択の迂回を防ぐ。AIワーカーへゲームオブジェクトを渡さず、ロード・戦闘切替・中止・期限切れ後の待機要求を実行しない。

新しい一括提出の要求IDはAIが提出単位で指定し、ホストが案内の操作へ一意なIDを生成して戦闘scopeと会話ターンに結び付ける。旧executeではAIが操作単位のIDを指定する。接続切替では実行済み操作と結果を継続情報へ含める。同じターンの再試行でも機械的な操作IDを維持し、登録済み結果を初期入力へ戻す。同ID・同内容は元の結果を返し、変更された内容は拒否する。MODは文章から目的を解釈したり、別IDの要求を意味的に同一と判断して統合したりしない。

標準エンジンでは従来のAPI往復上限内で情報取得と操作要求を処理する。1回のAI応答で受け取るツール呼び出しは情報取得と操作を合わせて40件までとし、情報取得バッチの最大8問い合わせとは分離する。40件を超える応答は、その応答内の処理を始める前に拒否し、既存のエラー通知経路で上限超過を表示する。それ以前の応答で登録済みの予約は取り消さない。この応答数制限は標準エンジンの方針であり、独自の相談実装へ強制しない。操作窓口にも要求・返却サイズ、ページ件数、待機列、相談内の呼び出し回数と返却量の上限を設ける。中止は未登録の待機要求を止めるが、既にゲームへ登録した命令の取消しとは扱わない。

最小試作の到達点は、通常相談で指定した発艦済みヘリに、指定座標への移動とソノブイ1発の投下予約をAI経由で登録し、登録結果を返せることだった。その後、AI経由の実ゲーム動作と承認後の予約登録を確認し、複数地点の計画も実モデルで提案・最終回答まで評価した。すべてのモデル・配置で実投下を検証したことは意味しない。実際の移動・投下はゲームが担当し、完了監視・再相談・発艦操作・深度変更は引き続き将来の拡張とする。

### 開発用の予約一覧と全消去

反復試験用に、指定した自軍ユニットの現在の予約列を取得し、全消去する開発APIとCLIを追加した。ゲーム側の予約アダプターと、対象解決・WIP／戦闘scope検証・結果確認のサービスを分け、既存のゲームスレッド受付から呼ぶ。AI向けgame_operationsには公開しない。取得は順序とソノブイ予約の地点・弾種・発数を含み、全消去はゲーム標準RemoveWaypointsを使って手動予約も消す。実行中の相談や設定編集中は消去を拒否する。物理投下・消費済み弾薬の巻き戻しや完了監視は提供せず、一時停止中の未実行予約で反復試験するための補助とする。

## 13. 操作の提案とユーザーによる承認（現行実装）

本節は承認・失効の共通基盤と、旧executeの単一案互換経路。新しい完全な計画の一括提出・選択は第15節、マッププレビューは第16節に従う。

操作定義に`RequiresApproval`を持たせ、AI向けカタログでも`requires_approval`として公開する。承認の要否はホスト側の定義から判定し、AIが指定する引数や回答文では変更できない。内蔵ソノブイ投下予約は承認必須とする。公開プロバイダーAPIの必須インターフェースや通信方式は変更せず、標準エンジン・独自相談実装のどちらも同じ操作受付を使う。

互換経路のexecuteは、引数と現在の候補を検証して`status: proposed`、`registered: false`を返す。ゲームへの登録はまだ行わない。1回の相談で受け取った要求は順序付きの提案へまとめ、相談が正常に終わった時点で確定する。承認必須の操作が1つでもあれば提案全体を保留し、含まれる他の操作も先行実行しない。承認不要の操作だけの提案は、正常終了時に共通受付が実行する。AIの通信をユーザー承認待ちのまま保持しない。

履歴の回答の下には小さな「提案を確認…」ボタンを置き、確認画面で対象・操作内容・地点と「戻る」「採用」を表示する。戻るは提案を実行せず閉じる。採用後は履歴のボタンを非活性の「採用」1つへまとめ、元のAI回答は変更しない。部分失敗や結果不明の内部判定と二重実行防止は維持し、失敗内容と完了件数はボタン名とは別に確認画面と履歴へ表示する。共通の文言は予約登録に限定せず、他の操作にも使える表現とする。確認画面を表示している間は別の相談を開始しない。

説明文は各操作実装が実際の保留要求から構築する。共通層は同一操作の要求を表示用にまとめて実装へ渡し、返された説明を並べるだけとする。UI部品や確認画面の制御は操作実装に持たせない。ソノブイ操作は対象ヘリごとの予約件数・弾種・地点を説明し、実装が保証する末尾追加と現在深度設定の利用を明記する。表示上の集約によって実行順序は変えない。

承認時にはWIP・対象・操作可否・情報公開設定・全件分の利用可能弾数をゲームスレッド上で再検証する。事前検証で拒否した場合は1件も登録しない。検証後は元の要求順で登録し、途中の失敗では後続を止め、登録済み件数とエラーを確認画面に示す。ネイティブ登録はトランザクションではなく、既に登録した予約を巻き戻すために既存予約を消去しない。予期しない例外は既存の障害処理へ表面化させ、結果不明の要求を再実行しない。二重クリック・同一要求IDの再送で登録を重複させない。

相談の失敗・中止・未完了、履歴の消去・表示件数上限による削除、アドバイザーの再起動、戦闘・ロードの切り替えでは未承認の提案を失効させる。通常のウィンドウ開閉では回答済みの提案を維持する。登録済みのゲーム予約はこれらの処理では消さない。

明示的な調査命令を送る開発APIの`POST /v1/operations`は、従来どおり直接登録する試験入口として維持する。この入口をAIツールや外部相談実装へ公開せず、開発APIによる通常相談はゲーム内相談と同様にユーザー承認を待つ。開発APIから承認を代行する口は追加しない。


### 往復上限での未完了終了

標準エンジンは往復上限または取得情報量の上限に達すると、最終回答用の追加通信を行わず、未完了として終了する。最後の許容応答が通常の最終回答なら正常完了とする。操作がない助言でも、上限まで情報取得が続けば回答なしで終了する。上限を理由とする自動再試行・上限延長・サブ接続への切り替えはしない。

実行部は終了理由を構造化した結果で共通ホストへ返し、共通側が通常完了と未完了を区別する。未完了の相談からの未承認提案は全件失効させ、承認不要の操作も自動実行しない。部分計画の承認ボタンは表示せず、未完了と提案失効を履歴に示す。以前にゲームへ登録済みの予約は変更しない。回答が完成していないため、この相談は次回送信する完了会話には含めない。通信エラー・予期しない例外・ユーザー中止は従来の別経路を維持し、上限終了として隠さない。

全通信ログには outcome=incomplete と completion_reason、開発用APIには state=incomplete と結果内の終了理由・利用量を記録する。CLIも未完了を終端状態として保存し、非ゼロで終了する。独自相談実装へ標準エンジンの往復方式を強制しない。

## 14. 用途別ツールと共通読み取り受付（2026-10-23更新）

標準エンジンはquery_situation、list_operations、describe_operation、get_operation_candidates、propose_operation_plansを定義と処理担当の組として登録する。相談エンジンは登録済みの名前へ要求を渡して結果を受け取り、各プロバイダーは任意長の定義一覧を通信形式へ変換する。操作ごとのツール追加や固有引数の解釈を共通エンジンへ持ち込まない。操作のスキーマと引数検証は操作受付、戦況のquery別定義と検証は戦況担当が所有する。

query_situationは従来のrequests配列とqueryごとのanyOfを保持する。操作ツールは用途ごとの引数だけを公開し、source／actionをAIに設定させない。操作定義・候補のoperation_id等の必須項目は維持する。propose_operation_plansは第15節の一括提出から承認・再検証へ委譲し、読み取りからは提案を作成しない。strictは有効化せず、モデルでの遵守率や往復削減は別途検証する。

操作を計画する場合はget_operation_candidatesで、対象操作の定義（引数・plan_policy・承認条件）とライブ候補を同じ応答へ返す。既存の候補・ページング項目は維持し、operationへdescribe_operationと同じ定義を追加する。空の候補や後続ページにも定義を含め、送信済み管理や新しい引数・ツールは増やさない。定義だけの照会にはdescribe_operationを残す。AdvisorOperationsが登録済み操作のDefinitionとCandidatesを組み合わせ、各コマンドの契約・承認と実行時の検証・プロバイダーの責務は変えない。旧action=candidatesにも同じ結果を返すが、開発APIの直接候補取得は既存形式を維持する。

同じAI応答での呼び出し例（各IDは同じ相談で取得済み、API固有の外側の形式は省略）:

```json
[
  {"name":"query_situation","arguments":{"requests":[{"query":"get_movement_plans","ids":["own_unit_1","own_unit_2"]}]}},
  {"name":"get_operation_candidates","arguments":{"operation_id":"seapower.schedule_sonobuoy_drop","target_ref":"unit:1029"}},
  {"name":"get_operation_candidates","arguments":{"operation_id":"seapower.schedule_sonobuoy_drop","target_ref":"unit:1030"}}
]
```

各読み取りの担当が内部の共通読み取り要求へ変換し、同じAI応答の独立した要求を一括処理する。応答のresultsは要求順で、index（0開始）とstatus=ok／error、dataまたはerror.codeを返す。操作照会は各呼び出し1項目として扱う。共通受付が元の呼び出しIDに分配し、各呼び出しのindexを0開始へ戻す。提案は別経路で送信順を保持する。

既存の外部標準アダプターはIStandardAdvisorExtensionのままなら従来のquery_game／game_operationsを受け取る。新しいIAdvisorToolListExtensionへ任意で移行するとConsultationInput.ToolsJson一覧を使う。旧形式のスキーマ合成だけを互換担当へ隔離し、読み取り受付・上限・承認は共有する。公開済みの必須メソッド、コンストラクター、assembly／contract versionは変更しない。独自相談のKnowledge／Operations窓口と手順は維持する。一括送信モードでは戦況用ツールを一覧から省き、WIP無効時には操作ツールを省く。

独立した項目だけを同じバッチへ入れる。配列内で直前の結果を引数へ参照するDSL・変数展開・自動再照会は設けない。未知の操作IDや対象IDが必要なら次のAI応答で要求する。操作の選択、配置、複数ユニット間の割り振りはAI、利用条件と引数定義は各操作が所有する。共通受付は艦種・機数・作戦の意味を解釈しない。

形式・件数・返却量と結果対応は共通受付が管理する。1応答中の読み取りは合計8項目、1要求16,000 B、1応答48,000 B、初期入力を含む読み取り合計160,000 B。既存の戦況取得予算・操作サービス予算も下位で維持し、実行提案を含むAI応答全体の40呼出し上限は別途適用する。引数やIDの誤りは項目ごとのエラーとし、成功した別項目は返す。外形や全体予算の不正はバッチ全体のエラー。内部不具合・予期しない例外を通常エラーへ変換しない。

戦況は相談開始時にコピーしたプレイヤー既知情報、操作候補は照会時の最新の自軍情報を返す。操作照会は既存の非同期ゲームスレッド経由で実行する。共通側でゲームスレッドを待機させない。合成応答に入る操作結果のバイト数を先に予約し、戦況取得へ残りの予算を渡す。兵器・センサー性能や経路の初回送信記録は、合成して返せる予算内であることが確定してから更新する。大きすぎた応答の再取得時に、未送信の資料定義が失われることを防ぐ。

標準アダプターは提示されたツールJSONをそのまま各サービスの形式へ変換する。独自相談の公開必須インターフェースと同期Knowledge／非同期Operationsの分担は変更しない。従来の直接戦況取得は従来のエラー仕様を維持し、共通受付だけがホスト指定の部分応答モードを利用する。開発APIのinputは標準エンジンが実際に準備したツールを記録し、各取得担当の要求・結果は従来のretrievals／operationsへ記録する。

一括取得をデータ構造として可能にする実装であり、実モデルがどの程度まとめるか、往復数・トークン数が改善するかは別途比較する。操作ID固定の先読みや追加のモデル試行はこの実装に含めない。

## 15. 複数案の一括提出と選択（2026-10-23実装）

### 確定した方針

1回の相談で取得した戦況・操作情報を利用して、複数の案を提示できる基盤へ拡張する。「案」はユーザーが確認・選択する計画の単位であり、案の中に含まれる予約件数やツール呼び出し数とは分ける。例えば、ソノブイ10地点への投下要求をまとめた計画は1案として扱える。

提案数の条件は各コマンドの定義が最小・最大として宣言し、共通基盤がAIへの提示と受理結果の検証を担当する。固定数も範囲指定も同じ仕組みで扱う。件数の検証は当該コマンドの操作案を作成する場合に適用し、操作の照会だけで案の生成を必須にしない。

| コマンド例 | 最小提案数 | 最大提案数 |
| --- | ---: | ---: |
| A：1案限定 | 1 | 1 |
| B：3案限定 | 3 | 3 |
| C：1〜3案 | 1 | 3 |

AIはユーザーの目的と取得した状況から各案の内容・違い・比較軸を考える。共通側に特定の操作用の案の種類を列挙せず、全コマンドへ一律に2案を要求する方針にも固定しない。提案数の条件は操作定義のオンデマンド取得に含める。プロンプトとツール定義を契約に合わせて整理し、受信側でも条件を検証する。

生成する案の数と、ユーザーが選択・実行する方式は別の仕様とする。生成数は上記の最小・最大指定を維持し、選択方式は各コマンドが次の2種類から宣言する。

| 選択方式 | ユーザーの操作 |
| --- | --- |
| 単数選択 | 提示された案から1案を選択して実行する |
| 複数選択 | 提示された案から1つ以上を選択して実行する |

共通側が宣言に応じた選択UIと選択数の制御を担当する。選択数に任意の最小・最大を指定する仕組みは今回導入しない。複数選択でも選んでいない案は実行せず、選択した案の組み合わせについては実行前に各コマンドが残弾などの条件を再検証する。

### 一括提出の契約

標準エンジンは`propose_operation_plans`を1回呼び、提出IDと全案をまとめて受け取る。各案は複数ユニット・複数種類の操作を含める**完全な計画**とし、操作種類ごとに案を分割しない。案の作成→操作の追記→提出完了という段階的なプロトコルも導入しない。

```json
{
  "request_id": "patrol-1",
  "plans": [
    {
      "plan_id": "a",
      "title": "推奨案",
      "summary": "配置と移動の主な理由・負担。比較軸はAIが考える。",
      "operations": [
        {"operation_id": "seapower.schedule_sonobuoy_drop", "target_ref": "unit:1029", "arguments": {"latitude": 26.5, "longitude": 127.1, "ammunition": "usn_ssq-41"}},
        {"operation_id": "seapower.schedule_sonobuoy_drop", "target_ref": "unit:1030", "arguments": {"latitude": 26.4, "longitude": 127.1, "ammunition": "usn_ssq-41"}}
      ]
    },
    {
      "plan_id": "b",
      "title": "代替案",
      "summary": "推奨案との違い。",
      "operations": [
        {"operation_id": "seapower.schedule_sonobuoy_drop", "target_ref": "unit:1029", "arguments": {"latitude": 26.45, "longitude": 127.2, "ammunition": "usn_ssq-41"}}
      ]
    }
  ]
}
```

`plan_id`は同一提出内で一意。`request_id`は提出全体の再送識別子で、個々の操作IDはホストが提出IDと配列順から生成する。各操作へAI生成のIDを重ねて要求しない。応答は`status: proposed`、`registered: false`、選択方式、案IDと操作数を返す。承認前にゲームへの登録済みとは報告しない。

標準経路での1相談は1組の完全な提出とし、受理後の追記・差替えは行わない。同じ提出の再送は結果を返し、異なる内容は`request_id_conflict`で拒否する。形式・案数・全案の検証に失敗した提出は一部だけ残さず、AIが訂正して再提出できる。正常な最終回答より先に実行しない。相談未完了時は全案を失効させる。

### 責務と操作ごとの条件

- `AdvisorOperationPlanBatch`はスキーマと外形検証、`AdvisorOperationGateway`は非同期ゲームスレッド受付と相談内ID正規化、`AdvisorOperations`は保管・承認・登録を所有する。新しい案管理と個別操作の引数処理をプロバイダーへ分散させない。
- コマンドは任意の`IAdvisorOperationPlans`から生成目標案数`target`、受理する最小・最大案数`minimum`／`maximum`、選択方式を宣言する。目標は受理範囲内であることを構築時に検証し、不正な宣言は例外にする。`describe_operation`および`get_operation_candidates`の操作定義にある`plan_policy`へ提示し、未指定は目標1案・受理1案・単数選択。ソノブイは目標2案・受理1～2案・単数選択とする。単なる照会・助言に案作成を強制しない。
- 条件の適用単位は、同じ対象への予約数ではなく、提出全体。含まれる全操作の最小値の最大と、最大値の最小を使う。AIは各操作の最大目標数を共通の受理範囲に収めた数を目標とする。目標数自体は受理条件にせず、範囲内で全案が有効なら目標未達でも受理し、追加案を要求・補完しない。受理範囲が両立しない宣言は`incompatible_plan_policies`、範囲外の提出数は`plan_count_out_of_range`で全体を拒否する。1案でも引数・残弾・対象と承認時の再検証は維持し、不正な案だけを除く部分受理は行わない。
- 選択方式が混在する場合は単数選択を優先し、全操作が複数選択を認めた場合だけ複数選択を許可する。特定の操作を別案から省いて、その操作の条件を回避する扱いにはしない。複数の独立した提案グループや案間依存のDSLは今回追加しない。
- 共通側は各案を独立して操作種別ごとに検証し、代替案どうしの弾薬を合算しない。選択後には選ばれた全操作を操作種別ごとにまとめ、各コマンドが現在の対象・合計必要数を再検証する。コマンドは他の種類の引数を解釈しない。
- 1案最大40操作、1提出最大8案。これらは資源保護用の外形上限で、生成数の指示は各コマンドの宣言を使う。既存の要求16,000 B、相談の操作予算、戦闘単位1,024操作レシート上限、1AI応答40呼出し上限も維持する。

既存の独自相談／旧標準拡張向け`game_operations`は`action: submit`で同じ提出を受け付ける。必須の公開インターフェースやassembly versionは変えない。旧`action: execute`の1操作ずつの受付は、既存クライアント互換の単一案経路として受理を維持し、新しい標準ツールには公開しない。両形式を同じ相談で混在させず、受理済み案を重複追加しない。明示的な開発APIの直接登録は従来どおり別経路とする。

### 承認画面と実行

承認待ちの複数案には、履歴へ「提案1: タイトル」「提案2: タイトル」のように案数分のボタンを並べ、それぞれから該当案を直接開く。既存のAI生成タイトルを使い、長い文字列は画面上だけ省略して承認画面に全文を表示する。ボタンは折り返し可能とし、1案だけの場合と採用後の表示は1ボタンとする。採用後は非活性の「採用」ボタンの横に、採用した案の元の番号とタイトルを「提案2: タイトル」の形で残す。既存のExecutionOrdersと各案の保持済み操作を照合して表示し、閲覧中の案やAIの最終説明から推定しない。複数選択では採用した案だけを元の提出順で表示し、同じ案に複数操作があっても重複表示しない。長いタイトルは折り返し、AIの回答本文・コピー内容は変更しない。部分失敗や結果不明では選択した案の表示と既存のエラー通知を併記し、事前検証でまだ採用できていない案や失効した案を採用済みとして表示しない。追加のAI項目・通信・プロンプトは不要。承認画面を開いたまま「前の提案」「次の提案」で切り替え、「提案 1 / 2」のように現在位置を示す。複数案では両方向とも末尾と先頭を循環し、1案だけなら前後操作を表示しない。タイトルの順序と説明はAIが決め、共通側で推奨理由を生成しない。

単数選択では表示中の案が操作対象となり、「採用」で承認する。表示と実行対象が食い違う選択状態は持たない。複数選択では表示中の案の「この提案を選択」チェックと選択件数を示す。前後移動や案の直接表示ではチェックを変更せず、同じ「採用」ボタンで承認する。選択方式やコマンドの種類でボタン名を切り替えない。初めは先頭案を選択し、承認を試みた後の通常の再確認ではその実行対象を復元する。履歴の案別ボタンから開いた場合は指定案を表示し、単数選択ではその表示案が実行対象になる。

実行ボタンの直上に太字の`操作対象: Hobby 1 (1029), Hobby 1 (1030)`を固定表示する。表示する対象は、実際に選択された案の保持済み操作の`target_ref`から提出順に集約し、同じ対象IDの重複だけを除く。同名ユニットはIDで区別する。名前は既存のローカルユニット参照から取得し、名前が取得できない場合やユニット以外の参照は元の参照を表示する。対象が多い場合は折り返して対象欄内でスクロールし、説明欄を末尾まで読まなくても実行対象を確認できる配置とする。単数選択は表示案、複数選択はチェック済みの全案に従い、未選択なら`操作対象: なし`とする。区切りは半角の`, `、括弧は半角の`()`を使い、対象数による「のみ」等の文言変更は行わない。追加AI情報や対象欠落の警告機能は今回導入しない。

閲覧番号と実行対象のチェックはUIの状態クラスだけが保持する。操作基盤は従来どおり案IDで説明・プレビューを返し、選択された案を再検証して登録する。プロバイダー、AIへのツール定義、個別コマンドへ画面遷移を持ち込まない。

前後移動に合わせて案の要旨・コマンド生成の説明・地図プレビューを一緒に更新し、説明のスクロールを先頭へ戻す。地図には表示中の案だけを描き、古い描画を破棄する。前後移動に追加AI通信やゲーム予約の変更は不要。複数選択時も全案を重ねない。選択していない案は登録しない。複数選択時は提出順、各案内は元の操作順で登録し、選択したクリック順で計画を並べ替えない。

複数案は自動実行不可とし、個別コマンドが承認不要でもユーザーの選択を待つ。1案だけで全操作が承認不要なら既存どおり正常終了時に自動実行できる。

承認前の再検証で残弾不足等になった場合は登録せず、案を保持したままエラーを示して別の選択を可能にする。実行開始後の失敗は従来どおり後続を止め、部分登録／結果不明を区別する。異なるコマンド間で共有する資源の完全なトランザクションは保証せず、各実行口のライブ検証を維持する。ゲーム予約を巻き戻すためにユーザーの予約を消去しない。二重承認・再送でも登録を重複させない。

実モデルが安定して複数案を提出するか、実ゲームUIでの比較・選択・プレビューの使い勝手は別途確認する。外部操作登録SDKの公開形式、独立した提案グループ、プレビュー全地点への自動ズームは今後の検討とする。

## 16. 共通マップ操作APIと承認用プレビュー

### 方針と提供する機能

座標の文字列だけでは操作予定の場所を判断しにくいため、承認時に実行予定を地図へ一時表示する。コマンド実装から使う共通マップ操作APIを設け、操作ごとに必要な描画と中央移動を指定できるようにする。特定の操作専用の描画機構にしない。

| 共通機能 | コマンド側が指定する内容 |
| --- | --- |
| 点の一時表示 | 緯度・経度、必要なラベル |
| 線の一時表示 | 緯度・経度の並び |
| 円の一時表示 | 中心の緯度・経度と半径（海里） |
| 中央移動 | マップ中央に表示する緯度・経度 |
| 一時描画の消去 | 当該プレビューに属する描画 |

描画と中央移動は独立した機能とする。承認プレビューの表示・再表示・案切り替えでは現在のマップ位置とズームを維持し、描画だけを更新する。中央移動は座標リンクなど、ユーザーが明示的に指定した操作で利用する。

これはコマンド実装者向けのAPIであり、AIへ新しいマップ描画ツールを公開する機能ではない。コマンドは保持された実行予定の引数からプレビューを作る。AIに同じ地点を描画用として別途生成させず、表示する計画と承認後に登録する内容を一致させる。地図表示を必要としないコマンドはプレビューを省略できる。

### 責務と寿命

| 担当 | 責務 |
| --- | --- |
| コマンド実装 | 承認用プレビューを求められた際、実行予定に対応する点・線・円を共通API経由で指定する |
| 提案管理・承認UI | 確認中の案と描画を対応付け、案の表示・切り替え・承認・終了に合わせてプレビューを開始・更新・消去する |
| 共通マップ実装 | ゲーム依存の描画と中央移動、描画オブジェクトの所有と後片付けを担当する |

操作実装へNoesisのUI部品や確認画面そのものを渡さず、共通のマップ操作契約を使わせる。今回の内部実装は操作が描画データを返す方式とし、描画・消去は共通側がプレビュー自身の所有範囲に限定して行う。

承認中はプレビューを維持する。複数案でも確認中の案だけを表示し、案を切り替える際に前の描画を片付ける。承認画面を閉じる、承認処理を終える、元の提案が失効する、アドバイザーを閉じる、戦闘・ロードを切り替える際には、共通側が一時描画を消去する。再確認時は保持された案から再表示できる。ウィンドウを閉じた際のプレビュー消去と、未承認提案自体の保持・失効は区別し、第13節の寿命方針を維持する。

プレビューはユーザーの手描き図形や登録済み予約から分離し、地図の操作を妨げず、ユーザーによる編集やセーブ保存の対象にしない。描画の消去はゲーム予約やユーザーの図形を削除しない。描画処理はゲーム／UIスレッド上で扱い、AI通信ワーカーからゲームの地図を直接操作しない。

### 今回の実装と残る確認

内部の`IAdvisorMap`は中央移動と描画を分離し、`Draw`が返す`IDisposable`を破棄すると、その呼び出しに属する図形だけを消す。描画データは点・線・円、色・線幅、点のラベルを表現する。円の半径は`RadiusNauticalMiles`で海里と明示する。ゲーム側はForegroundElementsへ非操作のMapPanelを追加し、線と円はMapPolylineで描く。円周はゲーム標準の球面座標計算で5度刻みに求め、描画要素に親地図を明示して、消去時には地図イベントの接続も解除する。

各コマンドは任意の`IAdvisorOperationPreview`から描画だけを含む`AdvisorMapPreview`を返し、自動移動先の指定は持たない。通常の操作インターフェースへ地図描画を必須追加しない。共通の提案管理が各コマンドの描画をまとめ、承認画面の寿命へ結び付ける。これらは内部契約であり、外部操作登録SDKの公開形式は引き続き未確定。

ソノブイ操作は受理済みの実行引数から投下地点を作り、対象名と対象ごとの投下順番号を付ける。機体ごとに、追加開始位置→投下地点1→地点2…を提案順の黄色い折れ線で結ぶ。共通のBattleReservationReader.ReadRouteが、ヘリ専用ではないObjectBaseからプレビュー表示時の現在位置と予約終点を読み、ゲーム・UI非依存の座標値だけを持つBattleReservationRouteを返す。予約なしはEndPositionがnull、予約機構が未準備なら結果自体がnullとなる。ソノブイ側が追記の仕様に従い、既存予約があればEndPosition、なければCurrentPositionを開始点として選ぶ。保存された生のウェイポイントを独自に再計算せず、相対移動・針路指定等もゲームが表示用に計算した終点を使う。開始点が取得できない対象は架空の原点を補わず、保持済み投下地点だけを表示する。予約があるのに計算済み経路が空の場合は不整合として例外を表面化する。

線は既存ポイントと同じ黄色・幅2で黒縁なし。線を先に、番号付きポイントを後に描き、別の機体同士を結ばない。線は地点の順序を示し、予約の追加・移動順序の変更・深度変更は行わない。画面再表示・案切替時に開始点を再取得し、毎フレーム追従やAIへの追加要求はしない。マップの表示位置とズームは動かさず、ユーザーが合わせた視点を維持する。承認画面の表示中はマーカーを維持し、毎フレーム再描画・再センタリングしない。「戻る」、実行開始、画面を閉じる、提案失効、WIP無効化、戦闘切替等で描画を消去する。予定位置の表示自体はゲーム予約・深度設定・残弾を変更しない。座標リンクは引き続き約3秒の単独マーカーを表示する。

模擬試験では、承認表示の位置と実登録座標の一致、任意コマンドの描画の集約、表示の開閉・切り替え・失効時の消去、他の表示との所有分離、描画異常時の後片付けと例外の伝播を確認した。ゲーム内の見た目、地図移動・ズームへの追従、線・円の実描画は実ゲームで確認する。選択UIは第15節に従う。全地点を見せる表示範囲調整と外部コマンド向け公開契約は今後の検討とする。探知範囲や航路など、図形が何を表すかの根拠は各コマンドが所有する。

AIが自由に地図へ図形を追加する機能、会話全体での図形管理、ユーザー管理への移管は以前の保留事項のままとする。今回の承認用プレビューへまとめて導入しない。


## 17. 相談内の参照情報と操作引数の正規化

AIが戦況内の資料IDや表示名を操作引数へ使う場合に備え、相談単位の共通参照情報を操作へ渡す。`AdvisorOperationReferences`は既存の自軍ID対応表と兵器の資料ID・元キー・表示名の対応を保持する。戦況取得側が情報選択後の自軍弾薬と対応資料から作成し、ゲームオブジェクトは保持しない。別相談や敵艦の標準装備資料から対応を借用しない。

ユニットの`target_ref`は共通の要求項目なので、共通受付が既存の自軍ID対応表で正規化する。操作固有の`arguments`は、任意の`IAdvisorOperationArgumentNormalizer`を実装したコマンドだけが解釈する。共通側は一意照合の機能を提供し、コマンド側が対象ユニットでその操作に使う弾薬候補を渡す。共通受付にソノブイの引数名や適格性判定を埋め込まない。正規化はゲームスレッド上で行い、副作用を起こさない。

ソノブイ操作では、正式な弾薬キーを優先する。既知の`weapon_reference_N`は対応するキーへ解決し、表示名は完全一致した候補の異なるキーが一つの場合だけ解決する。搭載弾薬表示と対応する性能資料の表示名に加え、操作候補の現在の表示名を照合できる。同じキーへの複数の一致は一候補とし、異なるキーが残る場合は`ambiguous_ammunition_reference`で拒否する。対象の搭載ソノブイ以外には置き換えず、残弾や投下可否で同名の別弾薬を選ばない。未知の値は既存の操作検証で拒否する。

正規化後に要求の重複判定と提案保存を行う。同じ要求IDで同じ対象・弾薬・引数を別表記で送っても提案を重複作成しない。異なる内容は既存の`request_id_conflict`を維持する。承認時には保存済みの正式IDを再検証し、表示名を再解決しない。名前や在庫の変化で別の弾薬へ振り替えない。

原要求は相談履歴と開発APIの記録に残し、補正した応答には`argument_resolutions`として引数名、補正前、補正後、理由を添える。既存の`target_ref_resolution`と併記できる。標準・独自の相談処理とも同じホスト受付を使う。公開SDKの必須契約、プロンプト、各プロバイダー、開発APIの直接予約登録は変更せず、直接登録は正式IDを要求する。


## コマンドの表示情報・多言語対応と設定内の閲覧（2026-10-24）

コマンドの一覧・詳細は登録済みの実装から読み取る。表示名や概要のために別の手書き一覧は作らない。IAdvisorOperation.Documentationがコマンド所有のAdvisorOperationTextを提供し、英語のname／summary／requirementsを必須とする。追加の言語と項目は任意で、要求言語・地域、基本言語、英語の順で選択し、翻訳先で欠けた項目は英語へ戻す。JSON不正・英語欠落・必須項目欠落は登録エラーとして扱い、英語フォールバックで隠さない。各言語は登録時に検証し、表示ごとのファイル読込はしない。

標準ソノブイコマンドはOperations/SonobuoyDrop/Localizationのen.json／ja.jsonをDLLへ埋め込み、両方を必須とする。承認説明も同じコマンド資源へ移す。共通の資源読込と項目単位の英語フォールバックにはAdvisorTextを再利用する。本体UIの翻訳が未対応でも、コマンド独自の対応言語を使えるように要求言語と解決済み表示言語を区別する。外部コマンドの登録APIは現時点で内部向けのままであり、公開APIは別途整備する。その際も自分のDLLへ埋め込んだ資源、または読み込んだ言語別JSONを渡せる構成を維持し、外部MODへ固定の配置パスや本体翻訳ファイルへの追記を要求しない。

設定のコマンドカテゴリは現在の画面に登録されたコマンドを一覧表示し、名前・内部ID・概要と詳細ボタンを提供する。説明・利用条件・承認要否は人向け、AIへの指示と定義JSONは実際の英語プロンプト／実引数定義をそのまま表示する。識別子・引数名・列挙値は翻訳しない。将来の全モード横断の静的カタログは今回導入せず、コマンドがない画面ではその旨を示す。

AdvisorOperations.InspectはWIP実行フラグとは独立した読み取り専用経路とし、候補照会・提案作成・実行セッションを開始しない。定義・承認要否・提案ポリシーはAI向けと同じ生成処理を使う。共通Function Calling定義も実通信と同じビルダーから読み、画面用にコピーしたJSONを別管理しない。現在のユニットが利用条件を満たすかは従来の候補照会・実行検証へ任せ、画面に同じ条件判定を作らない。

## ソノブイ操作の対象を搭載能力で判定（2026-10-24）

初期試作のヘリ限定を撤去し、現在のプレイヤーのユニットから、搭載弾薬にソノブイがある対象を候補とする。機種名・MOD名の対応リストは持たない。候補の抽出と弾薬列挙は同じ弾薬種別判定を使う。残数がゼロでも搭載種類を持つ対象は候補に残し、従来どおり使用不可の理由を返す。

ゲーム連携のBattleSonobuoyUnitは共通のObjectBaseを受け取り、予約登録・深度・経路・弾薬数の取得を共用する。AircraftとHelicopterはそれぞれの飛行中フラグを確認するが、機種そのものでは対象を拒否しない。その他のユニットも、ソノブイと利用可能な標準投下予約機構を持つ場合は同じ経路を使う。操作可否、予約機構の準備、編隊追従、競合命令、予約分を差し引いた残弾、1発投下可能な発射装置という既存の検証は維持し、実行・承認時に再確認する。

AI向け説明は操作可能な自軍ユニットへ一般化し、1回の操作で1発投下する引数定義は維持する。人向け概要・利用条件は機種をヘリに限定せず、数量の細かい表現を省く。実ゲームでのP-3Cの予約・投下は別途確認する。

## コマンドを正式機能へ移行（2026-10-24）

コマンドの有効／無効設定は設定の「コマンド」カテゴリに置き、一覧・詳細と同じ画面から保存する。設定は保存するまで実行可否へ反映せず、未保存変更の確認もこのカテゴリで扱う。WIPカテゴリには「現在、試験的な機能はありません。」を表示し、設定項目や保存ボタンは置かない。今後の試験機能の配置先としてカテゴリは維持する。

既存のUnitOperationsEnabledによる実行制御と承認・検証を維持し、新規・未設定時の初期値はONとする。保存済みON／OFFをそのまま読むため、旧キーwip_unit_operations_enabledは互換性のため保持する。保存形式の移行や二重の設定状態は作らず、内部保存メソッドだけSaveUnitOperationsへ改称する。外部コマンド登録の公開API化やP-3Cの実ゲーム動作確認はこのUI移行には含めない。
