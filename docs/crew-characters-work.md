# AI Crew：人物・就任機能の作業メモ（一時）

作成: 2026年11月5日 JST。作業ブランチ: `feature/crew-characters`。
開始点: `main` の `f434b80`（任務メッセージの保存・復元まで）。

Chatterの人物・就任に関する構想と、セーブデータへの保存・復元を含む作業を整理するための一時文書。構想のすべてを実装する約束や、実現方法を拘束する仕様書ではない。

既存の目的・責務境界とキャラクター事前登録の構想は、[AI CrewとChatterの設計メモ](ai-crew-chatter-design.md)、特に第9章を参照する。本書では今回の追加構想、判断の状態、次に検討する点を記録する。コードを読めば分かる詳細は転記しない。

## 1. 決定事項と現在の許可範囲

- Chatterの構想を整理・議論してから、Crewのセーブデータ対応へ進む。
- 今回の一連の作業には、Crewのセーブデータへの保存・復元も含める。保存対象の詳細は別途決める。
- 専用ブランチ `feature/crew-characters` で作業し、検討・決定事項を一時文書へ残す。
- ブランチと本書を作成・更新済み。追加ユニットへの自動就任（No.1）は仕様を合意し、実装の許可を得た。No.2は人物編集・個別再就任を実装する許可を得た。No.3以降は実装未着手。
- 第6章の6段階を暫定の作業順として採用する。作業を進めやすくするための順序であり、調査結果や実装負担に応じて分割・順序変更・見送りを判断できる。
- 段階的に実装範囲を判断する。効果に対して負担が大きい案は、簡略化・見送りも選択肢とする。
- 提案は、採用を確認できたものだけを決定事項へ移す。仕様の細部を今すべて確定しない。
- 現行UIの維持を優先条件にしない。既存の画面構成や操作方法に必要以上に縛られず、よりよいUIがあれば各段階で随時提案する。
- 画像だけのキャラクター登録と、就任後の人物情報の自由な部分編集を、下記の追加合意として扱う。人物編集は下記No.2の暫定UIで実装し、登録機能はNo.3で検討する。
- 画像本体はセーブデータに含めない。人物情報とセーブには、画像のファイル名や相対パスだけを持たせる。

本書は検討に合わせて更新する。作業完了時には、継続して必要な設計判断を既存の設計メモへ統合し、一時文書を整理・削除する方針。全構想の実現をブランチ完了の条件にせず、採用範囲に応じて統合時期を判断する。

### No.1：追加ユニットへの自動就任の合意事項

- 対象は現行の取得範囲に含まれる未就任者全員。編隊員も含め、取得対象そのものの拡張は今回は行わない。
- 設定は初期OFF。初回は手動の一括就任を行い、人物が正常に確定した後に自動確認を開始する。オプションをONにするだけで最初の就任は開始しない。
- 増加時刻は記録せず、確認時点の未就任者をまとめて対象にする。ONにする前から存在する未就任者も含む。
- Chatterの設定周期で確認する。ゲーム一時停止中はカウントを保持し、再生倍率には追従しない。発言の有無・発言資格・既存ユニットの参加ON/OFFに依存させない。
- 自動就任が成功した新規対象は参加ON。既存人物と既存対象のOFF指定は変更しない。未就任と、就任済みの参加OFFは別の状態。
- 「一時停止する」とエラー停止は就任・交信の両方を停止する。機能無効中も通信しない。自動就任オプションのOFFは追加の自動就任だけを停止し、既存の交信や手動就任は維持する。
- 手動の一括就任は、現行どおりゲーム一時停止中にも実行できる。
- 設定に「就任」カテゴリと「追加ユニットの自動就任」を追加する。既存の手動ボタン「自動就任」は「一括就任」へ改称する。保存・未保存変更の扱いは既存の設定操作に揃える。

実装では、発言と自動確認の機会に共通の時計を使い、未就任者がいない確認だけではAI通信しない。手動要求と自動要求を区別し、自動就任をOFFにした後は自動要求だけを取り消す。すでに送信した自動要求は通信を取り消せないが、その就任結果は適用しない。明示した手動要求と既存人物を維持するための扱いであり、生成プロンプトは変更しない。

### 追加合意：画像だけのキャラクター登録

- 顔画像だけを設定したキャラクターも登録できる。性別・国籍など、画像との整合性に必要な属性はユーザーが任意に入力する。
- 性別・国籍は、就任時にAIが名前などの人物情報を考えるための任意の指定情報とする。配属の適合性を判断するだけの情報には限定しない。登録キャラクター側で扱い、就任済み人物の常設属性や定期Chatter用の項目としてNo.2に追加しない。ゲーム由来のユニット所属国とは区別する。
- 入力済みの人物情報は保持し、未設定の人物項目をAIが補完して就任させる。既存の任意項目・AI補完の登録案で実現する。
- 入力項目の多寡にかかわらず「1登録＝1人のキャラクター」として扱う。画像だけの登録も、同じ登録を複数ユニットへ同時に重複就任させない。
- 今回の用途のために独立した顔画像プールや、同じ登録から複数の別人を生成する仕組みは追加しない。必要になった場合に改めて検討する。

画像付きの未完成な人物設定を補完する方式であり、登録キャラクターの画像を無条件に別人物へ流用する案ではない。画像IDと説明による独立した自動割り当ては、比較検討した代替案として今回の作業対象から外す。

### 追加合意：就任後の人物情報の部分編集

- 就任済み人物が持つ情報は自由に編集できる。No.2の編集項目は名前・画像・階級・性格を基本とし、性別・国籍は前項の人物生成用情報として登録側で扱う。理由なく編集項目を限定したり、軍制上の適合性を理由にMOD側で編集を制限したりしない。
- 通常の部分編集に、再就任やAI通信を要求しない。内部の人物IDや配属の整合性は維持する。
- 「就任済み人物の編集」「人物を交代させる再就任」「今後の就任に使う登録人物の編集」は意味を分ける。
- 編集の履歴反映に厳密性は求めず、現行の保持構造に沿う簡単な方式を選ぶ。編集後の人物表示・新しい発言へ反映し、過去履歴の人物情報や発言本文は書き換えない。登録元への反映はNo.3で検討する未決定事項。

### No.2：人物編集・個別再就任の暫定方針

- 参加ユニットの行で、Chatter参加チェックと、各枠内右端の「編集」ボタンを分離する。同じタブ内の人物画面で、名前・階級・性格・画像を編集し、AIによる個別再就任も要求できる。
- 通常の編集は保存で反映し、AI通信を行わない。未保存変更と保存成功の案内は、既存の設定画面に合わせる。
- 再就任は指定ユニットだけを対象に、生成成功後に旧人物を置き換える。失敗時は旧人物を残し、参加ON/OFFを維持する。旧人物の画像は引き継がない。
- 編集・交代前の生成結果や未表示通知を、新しい人物へ付け替えない。過去履歴は当時の人物・画像参照を保持する。
- 画像は保存確定時に通常ファイルへ取り込み、人物に相対パスだけを持たせる。画像の読込・描画を共通部品、取り込みコピーの管理と人物画面をCrewの責務とする。

UI・処理とも暫定決定。実装時に責務や複雑さの問題が見つかった場合は、理由と代替案を相談し、合意した画面へ固執しない。

### 追加合意：「性格」欄の自由記述

- 項目名は「性格」のままとする。「性格・話し方」などへの改称や、口調専用の別項目は追加しない。
- ユーザーの入力は最大255文字・複数行の自由記述とし、性格だけでなく話し方・呼び方・語尾などを含めてよい。
- MODは入力の保持と255文字の検証を担当する。内容を機械的に分類したり、一言の性格へ要約したりせず、人物設定としてAIへ渡して解釈を任せる。超過分を黙って切り捨てない。
- 自動就任時の短い性格も、ユーザーが詳しく編集した内容も同じ項目で扱う。AIによる自動生成向けの短い指定を、ユーザー編集へそのまま適用しない。

### 追加合意：画像の参照とセーブへの保存

- 画像本体は通常のファイルとして保管し、セーブへの埋め込みは行わない。画像に関して人物情報とセーブへ持たせるのは、ファイル名や相対パスの参照だけとする。
- ロード時に参照先の画像が見つからなければ、共通アイコンで続行する。外部パックの更新などで画像が変わることも許容し、保存時の顔を厳密に復元する保証は設けない。
- この用途のために独立した画像ID台帳、画像の重複排除、保存時の画像を固定する仕組みは設けない。登録人物から就任した人物へは画像の参照を引き継ぐ。人物・登録キャラクター自体の識別方法とは別の方針。
- 古いセーブの顔を維持するために、セーブ一覧を追跡したり、その画像を保持し続けたりしない。不要画像を判断する場合は、現在の登録人物・戦闘・履歴からの参照を考慮する。

Chatterは臨場感を出す機能であり、画像欠落を許容できる。画像の格納・復元までセーブ連携へ持ち込む複雑化と、セーブ容量の増加は今回の目的に見合わないため、必要画像だけを同梱する当初の推奨案も不採用とする。

具体的な保管先・相対パスの基準、外部パックの参照解決、画像の取り込み・削除のタイミングは、必要な段階で検討する。編集を登録元へ反映する範囲は引き続き未決定。過去履歴は前項の合意に従い書き換えない。

## 2. 現行実装で確認できた前提

以下は新しい決定事項ではなく、開始点の調査結果。

- 対象は自軍の水上艦・潜水艦・固定翼機・ヘリコプター。編隊の配下も就任対象に含む。取得元は地図の自軍一覧であり、未発進の搭載機まで含まれるかは未確認。
- 現在の就任操作は、Chatter参加チェックと無関係に未就任の対象全員を一括で要求する。就任を受理した対象は参加ONになり、既存人物の参加OFF指定は追加就任で戻さない。
- 人物、参加ON/OFF、発言資格は分離済み。発言資格は現在の編隊構成によって決まる。
- 新しく現れたユニットの就任は手動。就任済み対象の個別再就任、登録人物、外部キャラクターパックは未実装。
- Crewの人物・参加状態・履歴はメモリ内のみ。MOD共通のセーブ連携と互換性管理、任務メッセージ保存は既にあるが、Crewはまだ接続していない。

実装確認の入口は、`CrewChatter`、`CrewBattleSource`、`CrewBatch`、`CrewWindow`、`CrewPresentation`。細部はコードを確認する。

## 3. ユーザーが示した構想（採用範囲・詳細は検討中）

最初の提示は「こうなったらよい」というアイデアだった。第1章に記録した自動就任・画像だけの登録・就任後の部分編集は合意へ進んでいる。それ以外の詳細は引き続き検討中。

| 構想 | 現時点の希望・案 |
|---|---|
| 全ユニットへの就任 | 発言資格にかかわらず全員を就任対象にする。対象ユニット種別の拡張や未発進機の扱いは未確定 |
| 追加ユニットの自動就任 | 設定に「自動就任」を設け、初期就任後に増えたユニットへ自動で就任させる。確認タイミングはChatterの設定周期でよいという案 |
| 登録キャラクター | 好きな人物を登録・保存し、就任させたい。画像だけの登録・AI補完の合意は第1章を参照。優先就任などの従来案は既存メモ第9章も参照 |
| 他開発者のキャラクターパック | 別MODとして追加でき、DLLを必要とせず設定ファイルと画像だけで配布できる形を希望。名前を識別子にできるかという問いと、同名ならどちらかで上書きしてよいという許容案が出ている |
| 個別再就任 | 就任済みユニットだけを指定して再就任できるようにする。AIに任せる方法と、ユーザーが用意した人物を指定する方法を選びたい |
| 就任後の部分編集 | 就任済み人物の一部情報を直接編集する。編集の自由度・AI通信不要・履歴を維持する合意は第1章を参照。登録元への反映は未決定 |

従来の構想では、配属の適合性や未指定項目の補完は基本的にAIへ任せ、MODはIDや重複就任などの整合性を管理する。ユーザーによる就任後の直接編集には、配属判断のための適合性チェックを持ち込まない。

## 4. 提示済みの推奨案（まだ採用未確定）

### 責務と人物情報の寿命

- **登録人物の定義**、**戦闘中に確定した人物・配属・参加状態**、**Chatterの生成・表示**を分ける。登録内容の再利用と、戦闘中の人物の継続を両立するため。
- 登録内容へ補完結果を自動で書き戻さず、戦闘中の就任結果へ保持する案。明示設定の保持と未設定項目のAI補完自体は第1章の合意事項。
- 登録一覧は就任時の候補とし、定期Chatterへ全件を送らない。発言候補の就任済み人物だけを渡す。
- 画像は表示用とし、AIへの送信は行わない案。未設定画像には既存アイコンを使う。不正・読み込み失敗と未設定は区別する。

### キャラクターの識別と外部パック

- 表示名と固定の識別IDを分ける。名前は任意・変更可能で、同名の別人物もあり、セーブとの対応にも使うため。
- 例として `作者.パック:人物ID` のように、パックと人物の識別を組み合わせる案。具体的な形式は未決定。ユーザー登録のIDは自動発行する案。
- 上書きを認める場合は、同名ではなく同じ識別IDの定義を対象にする案。名前による上書きを許容するユーザー案も記録し、まだ決着した扱いにしない。
- 設定ファイル・画像だけのパックは実現可能と考えられる。有効なMODフォルダーを認識する既存経路はあるが、パックの探索・優先順位・画像管理・複数パックの併用は未実装・未検証。

### 個別再就任

追加ユニットの自動就任は第1章で合意済み。ここではNo.2以降の未確定案を扱う。
- 個別再就任では、新しい結果が正常に確定してから旧人物を置き換える。失敗時は旧人物を保持し、参加ON/OFFも維持する案。
- 指定した登録人物への手動配属では、配属先の選択をAIへ委ね直さず、必要な未設定項目だけを補完する案。
- 旧人物向けの生成結果や未表示通知を、新人物の発言に転用しない。過去履歴には当時の人物を保持する。

### セーブ対応の構成案

- 登録台帳や外部パックは戦闘セーブから独立させ、戦闘内の配属と補完後の確定人物情報を保存する案。元の登録IDも対応付けのために保持する。
- 登録・パックが更新されても、ロードした就任済み人物の名前や性格が突然変わらない構成を勧める。画像は第1章の合意に従い参照だけを保存し、画像本体の厳密な復元は求めない。
- 保存対象とする状態の範囲は別途決める。履歴、未表示通知、停止状態、周期の残り時間まで保存すると決めたわけではない。

## 5. 次に整理する論点

一度にすべて決めず、該当段階へ進む際に確認する。

- 各段階の具体的な実装範囲と、「全ユニット」の対象。未発進機を含める必要があるか。
- 登録値と言語設定の関係。既存の自動生成向け命名ルールをそのまま登録値へ適用しないか。性別・国籍の具体的な入力方法は、人物生成の任意情報という用途に沿ってNo.3で検討する。
- 同時重複就任の禁止を前提に、撃沈・再就任で配属が外れた人物を同じ戦闘中に再利用できるか。既に別ユニットへ就任中の人物を手動指定した際の扱い（拒否や配属変更など）。
- 登録の編集・削除を戦闘中の人物へどう反映するか。全項目未設定の登録を一覧でどう識別するか。
- 就任済み人物の部分編集を登録元へも反映するか。過去履歴を書き換えない方針の下で、編集中・生成中・未表示の発言との整合性をどう保つか。
- 外部パックの識別IDと重複時の扱い、ゲームのMOD優先順位との関係、画像参照の解決方法と所有・読み込み・破棄。画像の参照切れ時は第1章の共通アイコンへの切り替えに従う。
- 登録候補が多い場合の就任要求量、複数回の一括就任にまたがる重複防止。
- Crewのどの状態をセーブに保存し、どの状態はロード時に作り直すか。登録・配属の構成を踏まえて判断する。

## 6. 暫定の作業順と作業状況

2026年11月5日の議論で、以下の6段階を暫定順序として採用した。その後、No.1は第1章の仕様合意と実装許可を得た。画像だけの登録、就任後の部分編集、画像を参照だけで保存する方針についても第1章の合意はあるが、No.3以降の詳細全体や実装開始を承認したものではない。No.2は人物編集と個別再就任をまとめて実装する方針へ進んだ。既存メモ第9章の段階案に代わる現在の作業順とし、必要に応じて組み替える。

| 段階 | 内容 | この順序にする理由 | 状態 |
|---|---|---|---|
| 準備 | 専用ブランチと一時文書を用意し、構想と論点を整理する | 判断の状態を区別して次の作業へ引き継ぐ | 完了。議論に合わせて本書を更新 |
| 1 | 初期就任後の追加ユニットへの自動就任 | 既存の就任処理を基礎に、比較的独立して実装・確認できる | 実装済み。全768項目のテスト通過。実機未確認 |
