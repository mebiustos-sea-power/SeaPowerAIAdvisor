### No.1：追加ユニットへの自動就任の合意事項

- 対象は現行の取得範囲に含まれる未就任者全員。編隊員も含め、取得対象そのものの拡張は今回は行わない。
- 設定は初期OFF。初回は手動の一括就任を行い、人物が正常に確定した後に自動確認を開始する。オプションをONにするだけで最初の就任は開始しない。
- 増加時刻は記録せず、確認時点の未就任者をまとめて対象にする。ONにする前から存在する未就任者も含む。
- Chatterの設定周期で確認する。ゲーム一時停止中はカウントを保持し、再生倍率には追従しない。発言の有無・発言資格・既存ユニットの参加ON/OFFに依存させない。
- 自動就任が成功した新規対象は参加ON。既存人物と既存対象のOFF指定は変更しない。未就任と、就任済みの参加OFFは別の状態。
- 「一時停止する」とエラー停止は就任・交信の両方を停止する。機能無効中も通信しない。自動就任オプションのOFFは追加の自動就任だけを停止し、既存の交信や手動就任は維持する。
- 手動の一括就任は、現行どおりゲーム一時停止中にも実行できる。
- 設定に「就任」カテゴリと「追加ユニットの自動就任」を追加する。既存の手動ボタン「自動就任」は「一括就任」へ改称する。保存・未保存変更の扱いは既存の設定操作に揃える。

実装では、発言と自動確認の機会に共通の時計を使い、未就任者がいない確認だけではAI通信しない。手動要求と自動要求を区別し、自動就任をOFFにした後は自動要求だけを取り消す。すでに送信した自動要求は通信を取り消せないが、その就任結果は適用しない。明示した手動要求と既存人物を維持するための扱いであり、生成プロンプトは変更しない。

## 2. 現行実装で確認できた前提

以下は新しい決定事項ではなく、開始点の調査結果。

- 対象は自軍の水上艦・潜水艦・固定翼機・ヘリコプター。編隊の配下も就任対象に含む。取得元は地図の自軍一覧であり、未発進の搭載機まで含まれるかは未確認。
- 現在の就任操作は、Chatter参加チェックと無関係に未就任の対象全員を一括で要求する。就任を受理した対象は参加ONになり、既存人物の参加OFF指定は追加就任で戻さない。
- 人物、参加ON/OFF、発言資格は分離済み。発言資格は現在の編隊構成によって決まる。
- 新しく現れたユニットの就任は手動。就任済み対象の個別再就任、登録人物、外部キャラクターパックは未実装。
- Crewの人物・参加状態・履歴はメモリ内のみ。MOD共通のセーブ連携と互換性管理、任務メッセージ保存は既にあるが、Crewはまだ接続していない。

実装確認の入口は、`CrewChatter`、`CrewBattleSource`、`CrewBatch`、`CrewWindow`、`CrewPresentation`。細部はコードを確認する。

## 3. ユーザーが示した構想（採用範囲・詳細は検討中）

最初の提示は「こうなったらよい」というアイデアだった。追加ユニットの自動就任は第1章の合意へ進んでおり、それ以外の詳細は引き続き検討中。

| 構想 | 現時点の希望・案 |
|---|---|
| 全ユニットへの就任 | 発言資格にかかわらず全員を就任対象にする。対象ユニット種別の拡張や未発進機の扱いは未確定 |
| 追加ユニットの自動就任 | 設定に「自動就任」を設け、初期就任後に増えたユニットへ自動で就任させる。確認タイミングはChatterの設定周期でよいという案 |
| 登録キャラクター | 好きな人物を登録・保存し、就任させたい。顔画像・名前・性別・国籍・性格・階級などの任意項目、AI補完、優先就任については既存メモ第9章も参照 |
| 他開発者のキャラクターパック | 別MODとして追加でき、DLLを必要とせず設定ファイルと画像だけで配布できる形を希望。名前を識別子にできるかという問いと、同名ならどちらかで上書きしてよいという許容案が出ている |
| 個別再就任 | 就任済みユニットだけを指定して再就任できるようにする。AIに任せる方法と、ユーザーが用意した人物を指定する方法を選びたい |

従来の構想では、配属の適合性や未指定項目の補完は基本的にAIへ任せ、MODはIDや重複就任などの整合性を管理する。今回の追加案との具体的な組み合わせはこれから検討する。

## 4. 提示済みの推奨案（まだ採用未確定）

### 責務と人物情報の寿命

- **登録人物の定義**、**戦闘中に確定した人物・配属・参加状態**、**Chatterの生成・表示**を分ける。登録内容の再利用と、戦闘中の人物の継続を両立するため。
- 明示設定した人物項目はMOD側で維持し、未設定部分をAIが補完する。登録内容へ補完結果を自動で書き戻さず、戦闘中の就任結果へ保持する。
- 登録一覧は就任時の候補とし、定期Chatterへ全件を送らない。発言候補の就任済み人物だけを渡す。
- 画像は表示用とし、AIへの送信は行わない案。未設定画像には既存アイコンを使う。不正・読み込み失敗と未設定は区別する。

### キャラクターの識別と外部パック

- 表示名と固定の識別IDを分ける。名前は任意・変更可能で、同名の別人物もあり、セーブとの対応にも使うため。
- 例として `作者.パック:人物ID` のように、パックと人物の識別を組み合わせる案。具体的な形式は未決定。ユーザー登録のIDは自動発行する案。
- 上書きを認める場合は、同名ではなく同じ識別IDの定義を対象にする案。名前による上書きを許容するユーザー案も記録し、まだ決着した扱いにしない。
- 設定ファイル・画像だけのパックは実現可能と考えられる。有効なMODフォルダーを認識する既存経路はあるが、パックの探索・優先順位・画像管理・複数パックの併用は未実装・未検証。

### 個別再就任

追加ユニットの自動就任は第1章で合意済み。ここではNo.2以降の未確定案を扱う。
- 個別再就任では、新しい結果が正常に確定してから旧人物を置き換える。失敗時は旧人物を保持し、参加ON/OFFも維持する案。
- 指定した登録人物への手動配属では、配属先の選択をAIへ委ね直さず、必要な未設定項目だけを補完する案。
- 旧人物向けの生成結果や未表示通知を、新人物の発言に転用しない。過去履歴には当時の人物を保持する。

### セーブ対応の構成案

- 登録台帳や外部パックは戦闘セーブから独立させ、戦闘内の配属と補完後の確定人物情報を保存する案。元の登録IDも対応付けのために保持する。
- 登録・パックが更新されても、ロードした就任済み人物の名前や性格が突然変わらない構成を勧める。画像の参照切れなどの扱いは未決定。
- 保存対象とする状態の範囲は別途決める。履歴、未表示通知、停止状態、周期の残り時間まで保存すると決めたわけではない。

## 5. 次に整理する論点

一度にすべて決めず、該当段階へ進む際に確認する。

- 各段階の具体的な実装範囲と、「全ユニット」の対象。未発進機を含める必要があるか。
- 登録項目・性格や話し方の記述範囲・登録値と言語設定の関係。既存の自動生成向け命名ルールをそのまま登録値へ適用しないか。
- 重複就任を禁止する期間と範囲。参加OFF・撃沈・再就任で外れた人物を再利用できるか、既に別ユニットへ就任中の人物を手動指定したらどうするか。
- 登録の編集・削除を戦闘中の人物へどう反映するか。全項目未設定の登録を一覧でどう識別するか。
- 外部パックの識別IDと重複時の扱い、ゲームのMOD優先順位との関係、画像の所有・読み込み・破棄。パックが欠けたセーブをロードした場合の扱い。
- 登録候補が多い場合の就任要求量、複数回の一括就任にまたがる重複防止。
- Crewのどの状態をセーブに保存し、どの状態はロード時に作り直すか。登録・配属の構成を踏まえて判断する。
