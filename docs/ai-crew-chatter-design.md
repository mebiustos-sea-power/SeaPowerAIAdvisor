# AI CrewとChatterの設計メモ

作成: 2026年10月30日。整理: 2026年11月7日 JST。

作業を再開するときに、目的・責務境界・採用理由・未解決事項を把握するための資料。現在採用している設計を記録し、今後の変更を拘束する固定仕様にはしない。実装の細部はコード、開発者APIの操作は[開発者向けガイド](developer-local-api.md#ai-crew-chatter-verification)を参照する。

## 1. 目的と対象範囲

**AI Crew**はユニットに架空の担当者を割り当てる機能全体、**Chatter（交信）**は戦況に応じた短い心情・感想・反応を届ける機能。人物の存在感と臨場感を重視し、毎回の状況説明や戦術助言を求めない。独立した発言、同じ応答内の掛け合い、沈黙のいずれも自然な結果として扱う。

現在の対象は自軍の水上艦・潜水艦・固定翼機・ヘリコプター。ユニット操作は行わない。将来の自律操作は構想段階であり、そのためだけの汎用基盤を先行して作らない。

既存機能の再利用自体を目的にしない。意味と責務が一致する処理を共有し、不自然な依存や変換が増える場合はCrew側に専用処理を置く。

## 2. 責務と依存方向

CrewはAdvisorと同じMODに含まれる独立した機能。戦術相談の履歴・プロフィール・相談ジョブ・操作カタログを交信へ持ち込まない。MissionCreatorは別MODであり、Crew専用のMODやDLLは追加していない。

| 境界 | 担当することと理由 |
|---|---|
| Crewの状態と生成契約 | 人物、参加状態、発言機会、結果の受理を扱う。ゲームや表示の都合から独立して判断できるようにする |
| ゲーム連携 | プレイヤーが知り得る事実をゲームスレッドで取得し、切り離した値を渡す。通信中にゲームオブジェクトへアクセスしない |
| UI | 入力・表示を担当する。ウィンドウの開閉を交信の開始・停止と結び付けない |
| MOD側の接続橋渡し | 登録接続・アダプター・診断ログをCrewの生成処理へ接続し、CrewがAdvisorの設定全体へ依存することを避ける |
| Shared | 用途をまたいで意味が一致する通信・保存・UI部品・ゲームの事実取得を置く。Chatter向けの選考や入力構成はCrewが所有する |

API接続の登録情報は共用し、Chatterが使う接続の割り当てと設定は独立させる。接続を二重登録せずに用途別のモデルを選べるようにするため。同じ接続を選べば、モデルと接続別プロンプトの編集も両方へ反映される。交信へ渡す生成指示とデータはChatter専用とし、Advisorの共通プロンプトや会話履歴は引き継がない。現在、Chatter用のフォールバック割り当ては設けていない。

## 3. 人物・参加状態・発言資格を分ける

担当者と参加ON/OFFは各ユニットに属し、発言資格は現在の編隊構成から決める。編隊長と編隊非所属の単独ユニットが発言し、個別指示中でも編隊に所属する配下は編隊長の交信範囲に含める。追従中かどうかで所属を読み替えない。

自動就任は、参加チェックと無関係に、配下を含む一覧の未就任ユニット全員を対象とする。就任結果を受理したユニットを参加ONにし、その後のチェックはChatterへの参加だけを管理する。参加OFFでも人物は保持し、追加就任で既存のOFF指定を戻さない。人物を用意する操作と、交信へ参加させる操作の意味を分けるため。追加ユニットへの自動就任は初期OFFとし、初回の人物確定後に自動確認を始める。全員が参加OFFでも未就任者の確認は続け、新しい就任の成功時は参加ONにする。対象を話させない意思と、自動処理全体を止める意思を区別するため。

就任要求も参加状態から分離し、就任と発言は別の生成機会で受理する。未就任者をまとめて生成でき、誰も発言しなくても就任は成立する。既存人物を交信のたびに作り直さず、対応付けには表示名やコールサインを使わない。

人物・配属・参加状態・停止状態と、階級表示順の累積判定は戦闘セーブへ保存する。ゲームの保存用固有IDで対応付け、登録元の編集や地図上の番号変更で就任済み人物を作り直さない。顔画像は独立したライブラリのIDだけを参照する。交信履歴・通知・生成途中の要求は持ち越さず、ロード後は、ゲームの一時停止解除後に初回の生成機会を設け、その完了後から現在の設定周期で待つ。雰囲気を楽しむ機能として人物の継続を重視し、過去の交信の再現までは求めない。ウィンドウの開閉や同じ戦闘内での参加OFFでは人物を破棄しない。

### 名前と階級の表示

所属国・ユニットの種類・役割・公開ブリーフィングを参考に、AIが名前・階級・性格を決める。表記は回答言語に合わせ、名前はフルネーム、階級は略称も許容する。国別の階級表や言語別の配置規則をMODが管理する方式は採用していない。

表示には通常名と階級を使い、半角空白を挟む。AIが作った完成形をそのまま表示すると、名前の省略や空白の欠落があったため、完成形は順序を判断する材料に限って使う。

完成形からAI自身に前後を答えさせる方式でも、その回答と実際の並びが食い違った。そこで、MODが階級文字列の前方・後方一致を読み取る方式を採用した。順序は人物ごとに保持せず、受理した就任結果の累積多数決で共通化する。少人数の初回結果だけに依存せず、追加就任のたびに見直すため。多数派が変わった際に既存人物の表示順も変わることは、統一感のために許容している。

表示位置は補助情報なので、判定できない表記は無効票として扱い、それだけで就任を拒否したり交信全体を止めたりしない。人物のID・名前・階級・性格など、就任そのものの検証とは分ける。共通順序を次のAI入力へ返して後続の判断を誘導することも避ける。票の扱いの詳細は実装・試験を参照する。

## 4. 発言材料と創作の境界

自然な人物表現につながる少量の材料を優先する。戦術分析用の詳細情報を網羅することは目的ではない。情報選択はChatter専用とし、Advisor側の選択値を共用しない。

- 自軍の状態と、プレイヤーが把握している接触・活動中の兵器・現在の警報を利用する。敵の非公開の実状態へたどらない。
- 天候・海況などはゲームが持つ事実を使い、局地状況や探知性能への補正をMODが推測して付け足さない。
- 艦隊共有の接触は、自艦が探知した証拠ではない。敵味方の判定と、艦種・機種などの識別状態も区別する。
- 警報は被弾や損傷、レーダー照射はミサイル発射を意味しない。活動中の兵器数や航空運用中の状態も、新規発射・命中・離着陸完了という出来事に読み替えない。
- 心情は架空でも、その根拠になる出来事・被害・行動実施・任務達成は創作させない。

公開ブリーフィングは人物を決める就任時に渡し、定期交信には全文を送らない。任務要約の生成・保持・再利用は別途検討する。入力項目や生成指示の実体はコードを参照する。

最近の発言は繰り返しを避ける材料として使い、過去の会話を覚えていることをプレイヤーへ要求しない。情報選択の変更後に、以前許可されていた情報が過去発言経由でAIへ戻ることも避ける。

## 5. 発言機会と掛け合い

担当者ごとに定期発言を義務付ける方式から、Crew全体で発言機会を持つ方式へ変更した。MODは頻度・候補の選考・受理検証を、AIは候補の誰が発言するかと人物表現を担当する。全員を必ず発言させず、一部の発言や沈黙を許容するため。戦況に含まれる編隊員をAIが発言者に選んだ実例があるため、発言できる候補を生成側の選択肢にも明示する。選択肢と受理検証は同じ候補一覧に基づかせ、状況説明の対象と発言資格を区別して伝える。

複数候補と共通の戦況を一括で送り、同じAPI応答で結果を受け取る。データを人物ごとに複製したり、結果の後に締めの文章生成を求めたりしない。沈黙は正常な結果であり、発言を埋める再送はしない。ただし、沈黙を生成した要求にも通信量は発生する。

前回の生成完了から次の生成開始まで、ユーザーが設定した実時間の間隔で固定して待つ。発言者の選考や掛け合いを促す回の抽選は、生成周期と分ける。ゲームの一時停止中は残り時間を保持し、再生倍率には追従しない。高倍率でも通信頻度が急増せず、一時停止中に同じ戦況の交信を繰り返さないため。就任の明示要求と、送信済み要求の完了処理は発言用の時計から分ける。

掛け合いを単に許可するだけでは実通信でほとんど起きなかったため、一部の機会で相手の感情への応答を積極的に促す方式を採用した。ユーザーが調整する確率は、掛け合いを促す回を選ぶ確率であり、実際の成立率の指定ではない。題材がなければ独立発言や沈黙も受理する。

掛け合いは同じ応答内で成立させ、提出順に表示する。助言・命令や新しい事実の主張より、受容・共感・異なる感情による反応を促す。通常回も掛け合い優先回も、口にした発言に統一する。内心の連続で交信としての印象が薄れたため、感情・性格の表現は発話へ載せる方針を選んだ。内心用の抽選や括弧の解析・除去処理は設けない。

## 6. UI・停止・使用量の考え方

有効化の入口だけをAdvisor設定に置き、参加対象・接続・交信設定・履歴はCrewの専用画面へまとめる。Advisorだけを使うユーザーには入口を表示せず、Crewの利用者は戦術相談を開かずに管理できるようにする。初回は有効化だけでは通信を始めず、就任操作を必要とする。保存済みの人物と参加状態を復元した場合は、停止状態を尊重して交信を再開する。

普段は短い通知を表示し、必要なときに専用履歴で読み返す。標準イベントログへ混ぜないのは、ゲーム由来の出来事とAIの感想を区別し、ゲームの重要な通知も埋めないため。通知はゲーム操作を妨げず、到着時にウィンドウを強制表示しない。顔画像は独立したライブラリから参照し、未指定・欠落時には共通アイコンを使う。

保存・未保存変更の確認・入力フォーカスなどの基本操作はAdvisor設定に揃える。細かな画面配置・文言・初期値はUIと設定のコードを参照する。

手動の一時停止と生成エラーは、参加対象・人物・履歴を保持したまま交信を止める。以前はエラーで対象のチェックが外れたため、再開の意図と対象の選び直しを分ける方式へ変更した。自動再送はせず、ユーザーの再開操作を待つ。機能全体の無効化は利用停止の意思として対象もOFFにし、再有効化だけでは通信を再開しない。

通信中に対象・編隊・戦闘が変わった場合は、就任情報と発言それぞれの妥当性を受理時に確認する。キャンセルだけに依存せず、別の戦闘や現在は発言できない人物へ古い結果を反映しない。エラーはログと画面へ出し、別接続への無言の切り替えや成功扱いで隠さない。

使用量は常用の判断材料として、生成要求の単位で集計する。複数人をまとめて生成するため、個々の発言へのトークン配分は行わない。不正・沈黙・反映されなかった応答でも通信は消費され得るので、履歴へ採用された発言数と使用量を切り離す。APIが使用量を返さなかった場合は、消費ゼロとみなさない。

## 7. 確認できたことと残る課題

B6の試験用コピーで一括就任、人物の継続、編隊を考慮した対象選択、通知・履歴、一時停止と再開を確認した。実通信では掛け合い優先回と通常回の両方を確認し、階級表示の方式変更後にも日英の順序と、追加就任による累積判定を確認している。候補外提出への対策後にも、戦況に編隊員が含まれる状態で、通常回・掛け合い優先回とも候補内の提出を受理した。選択肢の指定が全モデルの応答を保証するものではない。境界条件・古い結果の破棄・使用量などの再発防止はテストを参照する。

残っている事項は次のとおり。実装予定を確約する一覧ではない。

- **人物表現と事実性はモデル依存。** 掛け合いの成立を確認できても、未提供の細部の創作や、発話形式からの逸脱を完全に防げたとはいえない。会話の自然さ・事実性・形式の遵守は分けて評価する。
- **UIと長時間運用の確認範囲。** 全通知位置・解像度・UI倍率・他MODとの重なりを網羅した検証ではない。小規模なB6での結果を、大規模ミッションや長時間の自然さへ一般化しない。
- **別途検討する構想。** ブリーフィング要約、自律操作、外部キャラクターパックは現在の実装へ含めていない。人物の登録・編集・保存は実装済みであり、設計判断を9章に記録する。必要になった時点で目的と負担を見直す。

過去の候補・試行ごとの数値・旧仕様は本文へ重ねず、経緯が必要なときはGit履歴やローカルの試験記録を参照する。ローカル記録の例は `artifacts/crew-exchange-tuning-20261031/` と `artifacts/crew-rank-matching-20261101/`。

## 9. 登録人物と顔画像

好きな人物をChatterへ登場させるため、登録キャラクターと、戦闘中の就任済み人物を分ける。再利用する人物設定と、特定ユニットに就任した確定情報では寿命が異なり、登録の編集が過去履歴やセーブ内の人物へ波及することも避けるため。

| 管理対象 | 役割 |
|---|---|
| 登録キャラクター | 任意の人物情報、画像ID、AI就任への包含・優先、就任先、重複許可を永続保持する |
| 就任中の人物 | 登録値とAI補完を組み合わせた確定情報、任意の登録IDと画像IDを持つ。人物編集を登録元へ自動で書き戻さない |
| 顔画像ライブラリ | 人物や戦闘の寿命から独立して画像を所有し、取り込み・置き換え・明示削除を担当する |

名前・階級・性格の指定済みの値はMODが保持し、未設定部分だけをAIが補う。性別・国籍も人物自身の確定した指定として扱う。配属の自然さはAIへ任せ、MODは就任先の種別、ID、重複、古い結果の反映を制御する。国籍の異なる配属を一律禁止する対応表は設けない。

一括応答で人物の国籍・名前などの不整合が残ったため、登録候補のある就任では適合性評価、配属・階級、名前・性格の生成を分けた。就任は頻度が低く、通信増より整合性を優先できる。名前を作る段階へユニット側の国籍やブリーフィングを混在させず、決まった個人情報を渡す。候補がない場合は評価を省き、完成した登録人物の手動就任には通信を要求しない。

通常交信へ登録台帳全体や配属評価の説明を再送しない。担当者の編集と再就任も分け、交代で参加ON/OFFを勝手に変えない。生成途中の旧人物向け発言や通知を新人物へ付け替えず、過去履歴は当時の人物を保持する。

画像IDと登録キャラクターIDは独立させる。同じ画像を複数人物が利用でき、画像だけの登録キャラクターも作れる。画像を外すたびにファイルを削除する方式や、過去のセーブから使用画像を追跡する方式は採用しない。削除はライブラリの明示操作とし、欠落時は共通アイコンへ戻す。画像本体はAIや戦闘セーブへ含めない。

標準サンプルは登録ファイルがまだない場合だけ通常のユーザーデータとして取り込む。以後の編集・削除をアップデートで上書きせず、空のライブラリも維持する。組み込み定義との継続的なマージや、削除履歴の管理を不要にするため。将来のサンプル変更も既存利用者へ自動反映しない。

このブランチの採用範囲・確認記録・未実装の外部パックに関する論点は、[人物・就任機能の一時作業メモ](crew-characters-work.md)を参照する。外部パックや、自動生成した人物の登録への取り込みなどを追加する場合は、その時点で目的と実装負担を再評価する。
