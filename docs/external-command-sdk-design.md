# 外部コマンドSDKの設計案

更新日：2026年10月24日（JST）。本書は外部開発者向けの公開契約・共通支援の設計と実装状況を記す。作業ツリーでは公開契約と標準ソノブイの移行まで実装済み。固定した本体への独立した外部MOD追加と実ゲーム検証は未実施であり、完成したSDKの利用ガイドとは区別する。型名・メソッド名・配布構成は、外部サンプルによる検証に合わせて見直せる。

操作基盤全体の方針は[AIによるユニット操作の設計メモ](ai-unit-control-design.md)、現在利用できるプロバイダー拡張APIは[公開APIガイド](public-api.md)を参照する。外部コマンドの詳細な契約案は本書へ集約する。

## 1. 目的と現在地

目標は、第三者がSea Power AI Advisor本体を変更・再ビルドせず、自分のコマンドを開発・配布できること。標準ソノブイコマンドも同じ公開契約と登録経路を利用し、外部コマンドだけが共通支援を使えない構成にしない。

v0.17.0では、内部のコマンド登録、操作カタログと定義・候補の取得、複数案の提出、ユーザーによる比較・採用、地図プレビュー、予約登録が実装されている。v0.17.1公開版には第三者がコマンドを登録するSDKはないが、現在の作業ツリーでは第10節の公開契約と標準コマンド移行まで実装した。既存の`AdvisorApi.Register(IAdvisorExtension)`はプロバイダー登録用であり、`IAdvisorOperations`はプロバイダーからホストの操作受付を利用するためのサービスである。どちらも外部コマンド実装の登録口ではない。

今回の目標は既存の提案・承認・実行経路を外部へ開くこと。実際の移動・投下完了の監視、完了後のAI再相談、リアルタイム制御は後続の検討とする。予約登録の成功とゲーム内での作業完了は区別する。

## 2. 責務と依存方向

公開契約は「登録定義」「戦闘単位のコマンド実装」「本体が提供する共通支援」に分ける。

| 担当 | 所有する責務 |
| --- | --- |
| 外部コマンドの登録定義 | 識別子、説明、引数定義、表示用資源、承認要否、提案ポリシー、戦闘用実装の生成 |
| 戦闘単位のコマンド実装 | 対象候補、適用条件、引数の意味、資源の検証、承認説明、ゲーム・追加MODへの操作、実結果 |
| 本体の共通受付・相談処理 | AIへのツール提供、権限制御、要求の識別、参照解決、提案の寿命、重複実行防止、実行順と結果の集約 |
| 本体の承認UI | 案の比較・選択・採用、実行対象と結果の表示、プレビューの切り替えと後片付け |
| ゲーム連携の共通支援 | 自軍情報・予約経路などの読み取り、検証済みのゲーム操作支援、地図描画、ゲームスレッドへの接続 |

`SeaPowerAIAdvisor.Api.dll`は現在の方針を維持し、Unity・Noesis・Sea Power・Anchor Chain・特定のJSONライブラリへ依存させない。JSONの定義・引数・結果は文字列で渡し、共通の座標や参照は標準ライブラリだけで扱える値オブジェクトで表す。ゲーム連携の実装は公開契約に依存し、公開契約が本体内部実装を参照する方向にはしない。

外部MODは公開API DLLを参照する。本体実装DLLや内部ソースへの参照を要求しない。独自のゲーム操作が必要な外部MODは、ゲーム本体や自身のMODのAPIも利用できる。本体側が未知の操作をすべて実装する必要はない。

対象はユニットだけに固定しない。施設・編隊・独自システムなども扱える対象参照を用い、自軍ユニットのID解決は共通支援として提供する。兵科・機種ごとの継承や、全操作共通の弾薬引数を要求しない。

## 3. 登録と寿命

作業ツリーの公開APIに次の登録口を追加した。引数は`IAdvisorOperationExtension`実装。公開済みv0.17.1のAPI DLLには含まれない。

```csharp
AdvisorApi.RegisterOperation(new ExampleOperationExtension());
```

外部MODはAnchor Chainの起動処理から、AI Advisorの初期化後に定義を登録する。既存のプロバイダー登録が持つ有効MODの所有確認・依存関係・起動順の検証を共用する方向とし、重複IDや非対応APIバージョンを明示的な登録エラーにする。

| 契約案 | 内容 |
| --- | --- |
| `GetDefinition()` | ゲーム状態を変更せず、コマンドの説明・引数・表示情報・ポリシーを返す |
| `CreateSession(context)` | 現在の戦闘に結び付いたコマンド実装を生成する |

定義には、名前空間付きの一意なID（例：`author.mod.command`）、対応APIバージョン、AI向けの説明と引数JSON Schema、言語別の表示資源、承認要否、目標案数・受理範囲・単数選択／複数選択を含める。提案ポリシーは各操作の回数ではなく、代替となる計画の数と選択方法を表す。

定義は登録後に変更しない。静的な説明の参照と、現在の対象候補の照会を分ける。現在の設定UIと同様、コマンドの文書を読むだけで候補取得や操作を実行しない。戦闘外での全コマンド一覧など、新しい画面仕様は今回のSDK整備にまとめて追加しない。

実行用インスタンスとそのゲーム参照は戦闘単位とし、ロード・戦闘終了時に破棄する。外部側に相談IDや全体の実行履歴を管理させず、本体が失効・二重実行を制御する。ゲームへの照会・検証・操作は本体からゲームスレッド上で呼び出し、AIとの通信待機を分離する。

Anchor Chainは依存順の適用前に公開型を探索する。既存の外部プロバイダー例と同様、公開するエントリーポイントの型定義にAdvisor API依存を持ち込まず、APIに依存する実装型はinternal等で隠す。API DLLは本体同梱版を参照し、外部MODへ重複同梱しない。具体的な登録形と配布手順は外部サンプルで確認する。

## 4. コマンド側が実装する処理

以下の名前は責務を示す仮称。既存の内部契約を出発点とし、公開境界で必要な情報だけを渡す。

| 必須処理の案 | 役割 |
| --- | --- |
| `GetCandidates()` | 操作に対応する対象・選択肢と、現在の利用可否・理由を返す |
| `Validate(orders)` | 引数、対象の状態、複数操作を合わせた資源消費などを副作用なしで検証する |
| `DescribeProposal(orders, language)` | 採用前にユーザーが読む、当該コマンドの内容説明を作る |
| `Execute(order)` | 承認方針に従って本体から呼び出され、1件の操作とその実結果を返す |
| `Dispose()` | 戦闘用インスタンスが所有する参照・資源を片付ける |

戦闘用ハンドラーは最初の候補取得・検証などが必要になった時点で生成する。メタデータの閲覧だけでは生成しない。

候補に含めるか、現在利用可能か、実行直前にも条件を満たすかはコマンド側で判断する。共通のユニット取得は、ヘリ・飛行中などソノブイ固有の条件で対象を削らない。候補照会の成功を、後の操作成功の保証にはしない。

検証は次の段階を区別する。

- 提出時は代替案を個別に検証する。各案が12発を使う場合、代替案が2つあるだけで24発必要とは判定しない。
- 採用時は、実際に選択された操作をまとめて再検証する。複数案の同時採用が許されるコマンドでは、選択した案を合わせた消費量を確認する。
- 実行時も対象の消失や残数など、操作に必要な現在条件を確認し、実際の受付・登録結果を返す。

本体は選択された操作をコマンドごとにまとめて検証し、元の順序で実行する。複数コマンドにまたがる資源競合やゲーム操作全体を、原子的な取引として保証しない。途中で失敗した場合は、既に行った操作と未実行・結果不明を区別し、実行済みの予約やユーザーの予約を一括消去して帳尻を合わせない。

追加処理は、必要なコマンドだけが任意契約を実装する。

| 任意処理 | 責務 |
| --- | --- |
| 地図プレビュー | 実行予定の引数から点・線・円の描画データを返す |
| 引数の正規化 | 引数の意味を知るコマンドが、共通参照表と適格な候補から一意な補正を行う |

地図を使わない操作へ空のプレビュー実装を要求しない。共通受付へ弾薬の引数名や、個別コマンドの適格性を埋め込まない。

## 5. 本体が提供する共通支援

初期の候補は、既存の標準コマンドで利用実績のある次の範囲とする。公開メソッドや提供単位は、標準コマンドと外部サンプルの移行で必要性を確認して決める。

| 支援 | 公開する内容・境界 |
| --- | --- |
| 自軍ユニットの参照 | 正式な参照ID、表示名、現在位置、必要な状態。生のゲームオブジェクトを共通公開契約へ渡さない |
| 搭載弾薬の参照 | 正式ID、表示名、種類、残数、既存予約を考慮した利用可能数。使用可能かはコマンドが判断する |
| 予約経路の参照 | 現在位置、既存予約の終点、取得不能の区別。ヘリやソノブイ専用の取得処理にしない |
| 相談内の参照解決 | ユニットIDと別表記、兵器資料ID・正式キー・表示名の対応。一意に解決できる場合だけ補正する |
| 多言語表示 | コマンド所有の言語資源を解決し、対応言語がなければ英語へ戻す |
| 地図操作 | 点・線・円の描画と消去、明示的な中央移動。ゲーム側の描画と寿命管理は本体が所有する |

読み取りは、プレイヤー既知の情報と設定による情報選択の境界を維持する。相談開始時に固定した戦況情報と、候補照会・採用時に読み取る現在状態を区別する。外部MODから任意のゲーム処理を呼べることと、本体がAIへ提供する情報の範囲は別であり、このAPIを外部コードの隔離機構とは位置付けない。

予約がない状態は終点なしとして表し、予約機構の未準備・取得失敗とは分ける。不整合や例外を「予約なし」に置き換えて現在位置からの経路へ流さない。取得できない値は取得できないと返し、設計上の不整合は既存の例外・ログ経路へ表面化させる。

弾薬IDなどの補正では正式キーを優先し、候補内で一意に特定できる場合だけ資料IDや表示名を解決する。利用可能数を理由に同名の別弾薬を選ばない。補正後の正式参照を提案へ保存し、採用時に再び名前から別対象を選び直さない。

英語の表示資源は必須、他言語は任意、標準コマンドは英語・日本語の両方を用意する。資源はコマンドが所有し、埋め込み資源や読み込んだJSONを渡せる構成にする。英語欠落やJSON不正は登録エラーとし、翻訳フォールバックで隠さない。設定画面とAI向け定義は登録情報を共用し、手書きの別カタログを増やさない。

## 6. ゲーム操作支援と地図プレビュー

汎用の提案・承認処理と、ゲーム固有の命令登録を分ける。既存の「指定地点へ移動し、ソノブイを1発投下する予約」のように実績のある処理を、小さなゲーム連携支援として標準・外部コマンドから利用できるようにする。全ての兵器・予約・追加MODを一つの万能操作APIで表そうとしない。

標準ソノブイコマンドは対象の搭載能力・利用可否・資源・投下順序を扱い、共通支援はゲームの予約機構へ命令を渡す。現在の深度設定は情報として提供し、予約登録でユーザーが選んだ深度を変更しない。ソノブイ固有の方針を、全コマンド共通の受付へ移さない。

ゲーム側にない独自操作は、外部開発者がゲームや追加MODのAPIを使って実装できる。公開支援の不足を埋める際も、用途と責務が明確な機能を追加し、必要性が確認できない階層やサービス探索機構を先に増やさない。

地図プレビューは[既存の設計メモ第16節](ai-unit-control-design.md#16-共通マップ操作apiと承認用プレビュー)を基にする。コマンドはゲーム・UI非依存の描画データを返し、承認画面の表示・案切り替え・終了に伴う描画と消去は本体が行う。コマンドへNoesis部品やユーザーの図形を直接管理させない。

中央移動とプレビューは独立させ、承認画面の表示や切り替えで地図を自動移動しない。コマンドが必要とする明示的な中央移動の提供形は、描画とは別に決める。プレビューの更新は表示・切り替えの節目で行い、毎フレームの追跡やAIへの再問い合わせを標準動作にしない。

## 7. 標準・外部コマンドの共通化

標準ソノブイコマンドも、同じ登録定義、戦闘用インスタンス、検証、説明、プレビュー、実行契約を使う。標準側だけが内部の相談処理や承認画面を直接呼び出す経路を残さない。標準コマンドが必要とする共通支援は、外部側でも利用できるようにする。

標準コマンドを別配布のMODへ移すこと自体は目的にしない。本体同梱を維持しながら公開契約の利用者にできる。内部オブジェクトや実装クラスを一括してpublicへ変える対応は避ける。

既存プロバイダー拡張の登録・通信契約を維持し、コマンドの公開契約と混同しない。APIの互換性・バージョン方針は公開前に確認する。外部MODは公開API DLLを参照し、AI通信、ユーザー承認、要求の重複防止を独自に再実装しなくてよい構成にする。

## 8. 実装と検証の進め方

1. 既存の内部契約と公開APIの境界を整理し、登録定義・戦闘用実装・必要な支援を公開契約として用意する。
2. 標準ソノブイコマンドを同じ契約と登録経路へ移行し、既存の動作を維持する。
3. 本体とAPI DLLをビルドして固定し、別プロジェクトの外部コマンドサンプルを作る。
4. 固定した本体へサンプルだけを追加し、カタログへの表示からAIによる提案・採用・実際の操作まで検証する。
5. サンプルで確認した手順と制約を、外部開発者向けのビルド・登録・配布ガイドへまとめる。

サンプルは本体実装DLLや内部ソースを参照しない。追加前後で本体DLLとAPI DLLのハッシュが同じことを確認し、本体の再ビルドを必要としない追加経路を検証する。不足が見つかった場合は契約を修正して本体を作り直し、その版を固定して同じ確認を繰り返す。

受け入れ確認は次のとおり。

- 外部MODの追加だけでコマンドを発見でき、設定の一覧・詳細とAI向け定義が同じ登録情報を使う。
- AIが定義と候補を取得し、複数操作を含む提案を提出できる。承認対象の操作は採用前にゲームへ適用されない。
- 標準・外部とも採用時の再検証、正しい対象への操作、元の順序、実結果の返却を確認できる。
- 任意のプレビューを表示・切り替え・消去でき、地図の視点やユーザーの図形を変更しない。
- 英語フォールバックが機能し、不正な定義・重複ID・非対応版・不明確な参照を明示的に扱える。
- ロードや戦闘終了で古い実装・提案を失効させ、重複した要求による二重実行を防ぐ。
- 途中失敗を隠さず、既存のプロバイダー拡張と標準ソノブイの動作を維持する。

サンプルで追加する具体的なコマンドは未決定。既存の登録口を呼ぶだけの例ではなく、候補取得・検証・承認・実操作まで必要な公開境界を確認できるものを選ぶ。

## 9. 実装時に決める事項

- 公開型・メソッドの最終シグネチャ、JSONと値オブジェクトの境界、APIの互換性とバージョン。
- ゲーム連携支援の最小範囲と提供単位。別DLLへの分割や汎用サービス階層は先に確定しない。
- 外部サンプルの題材と配布構成、実ゲームでの検証手順。

本書は責務と判断根拠を共有するためのものであり、実装方法を固定する仕様書ではない。検証でより自然な構成が分かった場合は、その理由と公開契約への影響を確認して設計を更新する。


## 10. 公開契約・標準コマンド移行の実装状況

本節は作業ツリーの実装を示す。製品版・API AssemblyVersion・既存プロバイダーの契約番号は据え置き、既存プロバイダーの必須インターフェースやシグネチャは変更していない。

| 公開型・入口 | 内容 |
| --- | --- |
| `AdvisorApi.RegisterOperation(IAdvisorOperationExtension)` | 有効な外部MODからのコマンド登録。プロバイダーの`Register`とは別入口 |
| `OperationDefinition` / `OperationPlanPolicy` | 登録時に固定するID・引数Schema・表示言語資源・承認・目標案数と受理範囲・選択方式 |
| `IAdvisorOperationHandler` | 戦闘単位の`GetCandidates`・`Validate`・`DescribeProposal`・`Execute`・`Dispose` |
| `OperationOrder` | 正式な対象参照と引数JSON。操作の順序・要求ID・提案の寿命は本体が所有 |
| `IAdvisorOperationContext` | ゲーム支援・地図操作・登録されたコマンドの翻訳を提供 |
| `IAdvisorGameSupport` | 自軍ユニット、搭載弾薬、予約終点、現在のソノブイ深度、移動＋1発投下予約の登録 |
| `IAdvisorOperationPreview` | 任意。表示用の点・線・円を返し、承認画面が描画の寿命を管理 |
| `IAdvisorOperationArgumentNormalizer` / `IAdvisorOperationReferences` | 任意。相談内参照と適格な弾薬を用い、一意に解決できる引数だけ補正 |
| `IAdvisorOperationInstructions` | 任意。ゲーム状態に触れず現在のAI向け説明を返す。標準コマンドの一時プロンプト差替えを維持するために利用 |

座標・描画は従来のライブラリ非依存型をAPI DLLへ移し、コピーを増やさない。ゲーム・Noesisの実装は本体に残る。JSONは文字列として境界を越え、特定のJSONライブラリをAPI DLLの依存へ追加していない。

登録メタデータは共通カタログで検証・保持し、本体の`AdvisorRegisteredOperation`が公開契約と既存の提案・承認エンジンを接続する。標準ソノブイの`SonobuoyDropExtension`も同じカタログとブリッジを使う。既存の開発APIからの操作検証もこの経路へ接続される。

自軍情報は`BattleOperationSupport`が読み取る。汎用ユニット一覧をソノブイ搭載や飛行中で絞らず、情報設定の自軍・基地・地上部隊の許可範囲を守る。ソノブイ搭載の判断、機体の飛行状態、弾薬数・単発対応・提案の投下順序は標準コマンドが判断する。書込支援も実際の対象・弾薬・予約受付を再確認する。深度の指定引数は公開せず、プレイヤーが現在選んでいる設定を維持する。

予約経路は`battle_movement_plans`が有効な場合だけ取得する。無効なら既存予約の終点をプレビューへ使わず、提案された投下地点の順序を表示する。未準備は経路取得の`null`、既存予約なしは`EndPosition == null`で区別し、不正な予約経路は例外のまま扱う。

公開支援はゲームスレッドでのみ利用でき、戦闘終了・ロードによる失効後の利用を拒否する。作成済みハンドラーを破棄し、コマンドが直接描いた図形も所有する描画だけを片付ける。他コマンドの破棄が失敗しても残りの破棄と待機中要求の終了処理を進め、失敗自体は例外へ残す。

第1～2段階のオフライン確認では、API DLLだけを参照する既存試験クライアントを拡張し、登録・メタデータ閲覧・承認・再検証・二重実行防止・寿命・エラー伝播を確認する。これは第3～4段階の「固定した本体に独立した外部MODだけを追加して実ゲームで動かす」検証の代用にはしない。次の実装単位はその外部サンプルと検証である。
